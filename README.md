### <u>پیش‌گفتار</u>

اگر تا امروز به هر شکلی با کد یا حتی نوشتن یک سند مشترک با دیگران سروکار داشته‌اید، احتمالاً این تجربه را از سر گذرانده‌اید: فایلی به نام ‪final.docx‬، بعد ‪final_v2.docx‬، بعد ‪final_v2_REALLY_FINAL.docx‬، و در نهایت ‪final_use_this_one.docx‬. این دقیقاً همان مشکلی است که سیستم‌های کنترل نسخه، و در رأس آن‌ها Git، برای حل آن به وجود آمده‌اند: چگونه تاریخچه‌ی تغییرات یک پروژه را، به‌طور دقیق و قابل‌اعتماد، ثبت و مدیریت کنیم؛ چگونه چند نفر بتوانند هم‌زمان روی یک پروژه کار کنند بدون این‌که کار یکدیگر را از بین ببرند؛ و چگونه در صورت اشتباه، بتوانیم دقیقاً به هر نقطه‌ای از تاریخچه که بخواهیم بازگردیم.

داستان Git از یک بحران واقعی شروع می‌شود. تا سال ۲۰۰۵ میلادی، توسعه‌دهندگان هسته‌ی لینوکس، یکی از بزرگ‌ترین پروژه‌های همکاری‌محور نرم‌افزاری در تاریخ، از ابزاری تجاری و انحصاری به نام BitKeeper استفاده می‌کردند. وقتی شرکت سازنده‌ی این ابزار، به‌دلیل اختلافی بر سر مجوز استفاده، دسترسی رایگان جامعه‌ی لینوکس را قطع کرد، لینوس توروالدز (Linus Torvalds)، خالق هسته‌ی لینوکس، خودش را در وضعیتی دید که باید ظرف چند روز، جایگزینی برای این ابزار حیاتی می‌ساخت. هیچ‌کدام از سیستم‌های کنترل نسخه‌ی متن‌باز موجود در آن زمان، مثل CVS یا Subversion، سرعت و مقیاسی که برای مدیریت هزاران پچ (patch) هسته‌ی لینوکس لازم بود را نداشتند.

توروالدز، در عرض تنها ده روز، اولین نسخه‌ی Git را نوشت. اولین کامیت این پروژه، در تاریخ ۷ آوریل ۲۰۰۵ ثبت شد؛ و نکته‌ی جالب این‌جاست که تا آن لحظه، آن‌قدر از خود Git ساخته شده بود که خودِ همان کامیت هم با استفاده از Git ثبت شد. طراحی Git از همان ابتدا سه هدف اصلی داشت: توزیع‌شده بودن (یعنی هر توسعه‌دهنده یک نسخه‌ی کامل از کل تاریخچه‌ی پروژه را روی سیستم خودش داشته باشد، نه فقط یک سرور مرکزی)، سرعت بسیار بالا (به‌خصوص برای عملیات‌هایی مثل مقایسه و ادغام تغییرات)، و مقاومت در برابر خرابی داده (به‌طوری‌که هرگونه دستکاری یا خرابی در تاریخچه، بلافاصله قابل‌شناسایی باشد). تنها چند ماه بعد، خود هسته‌ی لینوکس با موفقیت به Git منتقل شد، و از آن زمان تاکنون، Git به استاندارد بلامنازع دنیای توسعه‌ی نرم‌افزار تبدیل شده است؛ امروزه بیش از هفتاد درصد از توسعه‌دهندگان دنیا، به شکلی، از Git استفاده می‌کنند.

نکته‌ی مهمی که باید از همین ابتدا روشن شود: Git و GitHub یک چیز نیستند. Git یک ابزار خط‌فرمانی است که روی کامپیوتر خودتان اجرا می‌شود و کاملاً مستقل از هر سرویس آنلاینی کار می‌کند. GitHub (و به همین ترتیب GitLab و Bitbucket) یک سرویس آنلاین است که مخازن Git را میزبانی می‌کند و ابزارهای اضافی، مثل رابط گرافیکی، مدیریت مسائل (Issues)، و بررسی کد (Pull Request)، به آن اضافه می‌کند. می‌توانید سال‌ها با Git کار کنید بدون این‌که حتی یک‌بار هم به GitHub متصل شوید؛ اما وقتی نوبت همکاری با دیگران می‌رسد، این سرویس‌ها نقش بسیار مهمی ایفا می‌کنند، و در این کتاب، جایی که لازم باشد، به هر دو جنبه می‌پردازیم.

در این کتاب، قرار است با Git از پایه‌ترین مفاهیم (حتی اگر تا امروز هرگز از خط فرمان استفاده نکرده باشید) تا پیشرفته‌ترین تکنیک‌هایی که تیم‌های حرفه‌ای نرم‌افزار هر روز از آن‌ها استفاده می‌کنند، آشنا شوید. مسیر این کتاب طولانی و کاملاً جامع است: از ثبت اولین کامیت گرفته تا شاخه‌بندی، ادغام تغییرات، بازنویسی تاریخچه، همکاری با ریموت‌ها، بازگرداندن اشتباهات، جست‌وجوی عمیق در تاریخچه، گردش‌کارهای تیمی حرفه‌ای، ابزارهای پیشرفته مثل زیرماژول‌ها و قلاب‌ها (hooks)، و در نهایت، نگهداری و بهینه‌سازی مخزن.

### این کتاب برای چه کسانی مناسب است

این کتاب برای هر کسی نوشته شده که می‌خواهد Git را، از صفر مطلق تا سطح حرفه‌ای، به‌طور کامل یاد بگیرد. اگر تا امروز حتی یک بار هم دستور Git اجرا نکرده‌اید، فصل‌های ابتدایی همه‌چیز را قدم‌به‌قدم و با مثال‌های بسیار ساده توضیح می‌دهند. اگر هم سال‌هاست به‌طور روزمره از Git استفاده می‌کنید، فصل‌های میانی و پایانی به سراغ نکات دقیق‌تری می‌روند: تفاوت واقعی بین merge و rebase، جست‌وجوی دودویی برای پیدا کردن باگ با bisect، نوشتن قلاب‌های خودکار، و مدیریت مخازن بزرگ و پیچیده.

### در این کتاب چه چیزی خواهید یافت

در فصل ۱، «آشنایی با اصول Git»، مفاهیم پایه‌ای مثل مخزن (repository)، کامیت (commit)، ناحیه‌ی مرحله‌بندی (staging area)، و درخت کاری (working tree) را می‌بینید، و Git را روی سیستم خود نصب و پیکربندی می‌کنید.

در فصل ۲، «چرخه‌ی پایه‌ی کار با Git»، یاد می‌گیرید چگونه یک مخزن بسازید، تغییرات را مرحله‌بندی و ثبت کنید، وضعیت و تفاوت‌ها را بررسی کنید، و با فایل ‪.gitignore‬ فایل‌های ناخواسته را کنار بگذارید.

در فصل ۳، «شاخه‌بندی و ادغام»، وارد یکی از قدرتمندترین ویژگی‌های Git می‌شویم: ساختن شاخه‌های موازی توسعه، جابه‌جایی بین آن‌ها، و ادغام (merge) تغییرات، به‌همراه نحوه‌ی تشخیص و رفع تعارض (conflict).

در فصل ۴، «Rebase و تاریخچه‌ی تمیز»، با روش دیگری برای ترکیب شاخه‌ها آشنا می‌شوید که تاریخچه‌ای خطی و خواناتر می‌سازد، و ابزارهای قدرتمندی مثل rebase تعاملی و cherry-pick را یاد می‌گیرید.

در فصل ۵، «کار با مخازن ریموت»، یاد می‌گیرید چگونه با سرورهای راه دور (از جمله GitHub) کار کنید: کلون کردن، دریافت و ارسال تغییرات، و مدیریت شاخه‌های ریموت.

در فصل ۶، «بازگرداندن تغییرات و مدیریت اشتباهات»، ابزارهایی می‌بینید که هر توسعه‌دهنده‌ای دیر یا زود به آن‌ها نیاز پیدا می‌کند: reset، revert، پنهان کردن موقت تغییرات با stash، و شبکه‌ی ایمنی نهایی، یعنی reflog.

در فصل ۷، «کاوش عمیق در تاریخچه»، یاد می‌گیرید چگونه در تاریخچه‌ی طولانی یک پروژه جست‌وجو کنید، ببینید هر خط از کد را چه کسی نوشته (blame)، و با جست‌وجوی دودویی (bisect) دقیقاً کامیتی را پیدا کنید که یک باگ را ایجاد کرده است.

در فصل ۸، «همکاری تیمی و گردش‌کار حرفه‌ای»، به سراغ دنیای واقعی همکاری می‌رویم: Fork کردن، Pull Request، بررسی کد، و مدل‌های گردش‌کار رایج مثل Git Flow و GitHub Flow.

در فصل ۹، «ابزارهای پیشرفته‌ی Git»، مفاهیمی مثل زیرماژول‌ها (submodule)، درخت‌های کاری چندگانه (worktree)، قلاب‌ها (hooks)، و بررسی جزئی مخزن (sparse-checkout) را می‌بینیم که در پروژه‌های بزرگ و پیچیده کاربرد پیدا می‌کنند.

و در نهایت، در فصل ۱۰، «بهینه‌سازی، نگهداری و امنیت»، یاد می‌گیرید چگونه سلامت مخزن خود را بررسی و حفظ کنید، عملکرد آن را بهینه کنید، و کامیت‌های خود را با GPG امضا کنید تا اصالت آن‌ها قابل‌اثبات باشد.

### آنچه لازم دارید

برای دنبال کردن این کتاب، تنها به یک کامپیوتر با سیستم‌عامل لینوکس، macOS یا ویندوز نیاز دارید که دسترسی به خط فرمان داشته باشد. در فصل ۱ نحوه‌ی نصب Git روی هرکدام از این سیستم‌ها را توضیح می‌دهیم. برای فصل‌های مربوط به همکاری از راه دور، داشتن یک حساب رایگان روی GitHub مفید خواهد بود، هرچند مفاهیم اصلی مستقل از هر سرویس خاصی توضیح داده می‌شوند.

هیچ دانش برنامه‌نویسی خاصی لازم نیست؛ Git برای مدیریت هر نوع فایل متنی، از کد گرفته تا اسناد، قابل‌استفاده است.

## فصل ۱

### <u>آشنایی با اصول Git</u>

پیش از آن‌که وارد دستورهای واقعی Git شویم، لازم است چند مفهوم بنیادین را بشناسیم که در سراسر این کتاب بارها به آن‌ها ارجاع می‌دهیم. در این فصل، نصب Git را روی سیستم خودتان انجام می‌دهید، هویت خود را به آن معرفی می‌کنید، و مهم‌تر از همه، سه ناحیه‌ی اصلی‌ای که هر فایل در Git از میان آن‌ها عبور می‌کند را با جزئیات کامل درک می‌کنید.

### ۱.۱ گیت چیست؟

گیت یک سیستم کنترل نسخه‌ی توزیع‌شده (Distributed Version Control System) است. بیایید این عبارت را تکه‌تکه معنا کنیم:

- کنترل نسخه یعنی Git تاریخچه‌ی کامل تغییرات یک پروژه را، در طول زمان، ثبت می‌کند. می‌توانید ببینید هر فایل در هر لحظه از تاریخچه چه شکلی بوده، چه کسی و چه زمانی آن را تغییر داده، و چرا آن تغییر انجام شده است.
- توزیع‌شده یعنی، برخلاف سیستم‌های قدیمی‌تر که فقط یک سرور مرکزی تاریخچه‌ی کامل را نگه می‌داشت، در Git هر نسخه‌ای که روی کامپیوتر هرکسی کلون شده، شامل کل تاریخچه‌ی پروژه است. این یعنی می‌توانید کاملاً آفلاین کار کنید، کامیت بسازید، شاخه بسازید، و تاریخچه را مرور کنید، بدون این‌که به هیچ اینترنتی نیاز داشته باشید؛ فقط زمانی که بخواهید تغییرات را با دیگران به اشتراک بگذارید، به یک اتصال شبکه نیاز پیدا می‌کنید.

این معماری توزیع‌شده، دقیقاً همان چیزی بود که در پیش‌گفتار گفتیم لینوس توروالدز برای مدیریت هسته‌ی لینوکس به آن نیاز داشت: سرعت بالا، کار آفلاین، و مقاومت در برابر نقطه‌ی شکست واحد (اگر سرور مرکزی از بین برود، هر کلون موجود روی هر کامپیوتری، کل تاریخچه را دارد).

<div style="text-align:left;">

```
$ git --version
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر نصب نبود، macOS به‌طور خودکار نصب ابزارهای خط‌فرمانی Xcode را پیشنهاد می‌دهد. روش دیگر، استفاده از Homebrew است:

</div>

### ۱.۳ معرفی خودتان به Git

پیش از ساختن اولین کامیت خود، باید به Git بگویید چه کسی هستید؛ این اطلاعات در هر کامیتی که می‌سازید ثبت می‌شود تا مشخص باشد چه کسی آن تغییر را انجام داده است:

</div>

<div style="text-align:left;">

```
$ git config --global user.name "Mehmet Lotfi"
$ git config --global user.email "mehmet.lotfi@gmail.com"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

فلگ ‪--global‬ به این معناست که این تنظیمات برای *همه‌ی* مخازن Git روی این کامپیوتر اعمال می‌شود، نه فقط یک پروژه‌ی خاص. اگر بخواهید برای یک پروژه‌ی مشخص (مثلاً یک پروژه‌ی کاری با ایمیل شرکتی متفاوت) نام یا ایمیل دیگری تنظیم کنید، کافی است از داخل همان پوشه‌ی پروژه، همین دستورها را بدون ‪--global‬ اجرا کنید؛ تنظیمات محلی همیشه بر تنظیمات سراسری اولویت دارند.

برای دیدن همه‌ی تنظیمات فعلی Git خود:

</div>

<div style="text-align:left;">

```
$ git config --list
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۱.۴ سه ناحیه‌ی اصلی Git

حالا به مهم‌ترین مفهوم این فصل می‌رسیم؛ مفهومی که اگر آن را کاملاً درک کنید، فهم تمام دستورهای Git در فصل‌های بعدی بسیار ساده‌تر می‌شود. هر فایلی که Git آن را ردیابی می‌کند، در هر لحظه، در یکی از سه «ناحیه» قرار دارد:

- درخت کاری (Working Tree): همان پوشه‌ی واقعی روی دیسک شماست که فایل‌ها را می‌بینید و ویرایش می‌کنید. این دقیقاً همان چیزی است که با یک فایل‌منیجر یا ویرایشگر متن می‌بینید.
- ناحیه‌ی مرحله‌بندی (Staging Area)، که به آن Index هم گفته می‌شود: یک ناحیه‌ی موقت و میانی است. وقتی فایلی را تغییر می‌دهید، آن تغییر ابتدا در درخت کاری است؛ با دستور ‪git add‬ (که در فصل بعد با جزئیات کامل می‌بینیم)، آن تغییر را به ناحیه‌ی مرحله‌بندی منتقل می‌کنید، یعنی می‌گویید «این تغییر آماده است تا در کامیت بعدی قرار بگیرد».
- مخزن (Repository): تاریخچه‌ی دائمی پروژه است که در پوشه‌ی مخفی ‪.git‬ ذخیره می‌شود. وقتی با دستور ‪git commit‬ کامیت می‌سازید، محتوای ناحیه‌ی مرحله‌بندی، به‌طور دائمی، به‌عنوان یک نقطه‌ی جدید در تاریخچه، در مخزن ذخیره می‌شود.

این مدل سه‌مرحله‌ای، یکی از تفاوت‌های اصلی Git با بسیاری از سیستم‌های دیگر است و به شما امکان کنترل بسیار دقیقی می‌دهد: می‌توانید ده فایل را تغییر دهید، اما فقط سه‌تا از آن‌ها را مرحله‌بندی و کامیت کنید، درحالی‌که هفت‌تای دیگر همچنان در درخت کاری، بدون کامیت، باقی می‌مانند. در فصل بعد، این جریان را با مثال‌های عملی کامل می‌بینیم.

### ۱.۵ Git محتوا را ردیابی می‌کند، نه فایل‌ها را

یک نکته‌ی مفهومی مهم دیگر، که در مستندات رسمی Git هم به‌صراحت به آن اشاره شده: بسیاری از سیستم‌های کنترل نسخه‌ی قدیمی‌تر، دستوری برای «شروع ردیابی یک فایل» داشتند که مشخصاً برای فایل‌های *تازه* استفاده می‌شد. اما دستور ‪git add‬ در Git، برای فایل‌های تازه *و* فایل‌های موجودی که تغییر کرده‌اند، دقیقاً به یک شکل عمل می‌کند: در هر دو حالت، یک «عکس فوری» (snapshot) از محتوای فعلی آن فایل می‌گیرد و آن محتوا را در ناحیه‌ی مرحله‌بندی قرار می‌دهد. Git، در سطح پایه‌ای‌اش، دنبال «تفاوت بین نسخه‌ها» نیست؛ بلکه در هر کامیت، اساساً یک عکس فوری کامل از وضعیت کل پروژه (به‌شکلی بسیار بهینه‌شده که فایل‌های بدون‌تغییر را دوباره ذخیره نمی‌کند) نگه می‌دارد.

### ۱.۶ ساختار پوشه‌ی ‪.git‬

وقتی یک مخزن Git می‌سازید (که در فصل بعد نحوه‌ی دقیقش را می‌بینیم)، Git یک پوشه‌ی مخفی به نام ‪.git‬ در ریشه‌ی پروژه‌ی شما می‌سازد. این پوشه، *کل* مخزن شماست؛ همه‌ی تاریخچه، همه‌ی شاخه‌ها، همه‌ی تنظیمات مخصوص همان پروژه، در همین پوشه ذخیره می‌شوند. اگر این پوشه را حذف کنید، کل تاریخچه‌ی Git آن پروژه، بدون هیچ راه بازگشتی، از بین می‌رود (اما فایل‌های واقعی درخت کاری شما دست‌نخورده باقی می‌مانند، چون آن‌ها مستقل از ‪.git‬ روی دیسک هستند).

می‌توانید محتوای این پوشه را ببینید (پس از ساختن یک مخزن در فصل بعد):

</div>

<div style="text-align:left;">

```
$ ls -la .git
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

در این کتاب، عمدتاً با دستورهای سطح‌بالای Git کار می‌کنیم که این ساختار داخلی را برای شما مدیریت می‌کنند؛ اما دانستن این‌که همه‌چیز در همین یک پوشه خلاصه می‌شود، به شما کمک می‌کند بفهمید چرا کپی کردن یک پوشه‌ی پروژه (همراه با ‪.git‬ آن) دقیقاً معادل کلون کردن کامل تاریخچه‌ی آن است.

### ۱.۷ حالا چه؟

در این فصل، Git را روی سیستم خود نصب کردید، هویت خود را به آن معرفی کردید، و مهم‌تر از همه، مدل سه‌ناحیه‌ای Git، یعنی درخت کاری، ناحیه‌ی مرحله‌بندی، و مخزن را با جزئیات کامل درک کردید. همچنین دیدید Git محتوا را ردیابی می‌کند، نه فقط فایل‌ها را، و ساختار پوشه‌ی ‪.git‬ را شناختید.

در فصل بعد، بالاخره دست به کار می‌شویم: اولین مخزن خود را می‌سازیم، اولین کامیت را ثبت می‌کنیم، و چرخه‌ی کامل روزمره‌ی کار با Git، از تغییر فایل تا بررسی تاریخچه، را قدم‌به‌قدم یاد می‌گیریم.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| git --version | نسخه‌ی نصب‌شده‌ی Git را نمایش می‌دهد. |
| git config --global user.name "NAME" | نام کاربری شما را برای همه‌ی مخازن این سیستم تنظیم می‌کند. |
| git config --global user.email "EMAIL" | آدرس ایمیل شما را برای همه‌ی مخازن این سیستم تنظیم می‌کند. |
| git config --global core.editor "CMD" | ویرایشگر متن پیش‌فرض Git برای پیام‌های کامیت را تنظیم می‌کند. |
| git config --global init.defaultBranch main | نام پیش‌فرض اولین شاخه‌ی مخازن تازه را تعیین می‌کند. |
| git config --list | همه‌ی تنظیمات فعلی Git را نمایش می‌دهد. |

</div>

## فصل ۲

### <u>چرخه‌ی پایه‌ی کار با Git</u>

در فصل قبل، مفاهیم نظری Git را دیدیم. حالا وقت آن رسیده که واقعاً دست به کار شویم: اولین مخزن خود را می‌سازیم، اولین کامیت را ثبت می‌کنیم، و چرخه‌ای که هر توسعه‌دهنده، صدها بار در روز آن را تکرار می‌کند، یعنی «تغییر بده، مرحله‌بندی کن، کامیت کن»، را قدم‌به‌قدم یاد می‌گیریم.

### ۲.۱ ساختن اولین مخزن با ‪git init‬

بیایید یک پوشه‌ی تازه برای پروژه‌ی خود بسازیم و آن را به یک مخزن Git تبدیل کنیم:

</div>

<div style="text-align:left;">

```
$ mkdir my-project && cd my-project
$ git init
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

Git پاسخ می‌دهد:

</div>

<div style="text-align:left;">

```
Initialized empty Git repository in /home/ali/my-project/.git/
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

همان‌طور که در فصل قبل گفتیم، این دستور یک پوشه‌ی مخفی ‪.git‬ می‌سازد که از این لحظه، کل تاریخچه‌ی پروژه‌ی شما را در خود نگه می‌دارد. توجه کنید که ‪git init‬ می‌تواند روی یک پوشه‌ی *موجود* و پر از فایل هم اجرا شود؛ لازم نیست حتماً از یک پوشه‌ی خالی شروع کنید.

### ۲.۲ ساختن اولین فایل و بررسی وضعیت

بیایید یک فایل ساده بسازیم:

</div>

<div style="text-align:left;">

```
$ echo "# My Project" > README.md
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

حالا با دستوری که در طول کار روزمره‌ی خود با Git، بیشتر از هر دستور دیگری اجرا خواهید کرد، وضعیت فعلی مخزن را بررسی می‌کنیم:

</div>

<div style="text-align:left;">

```
$ git status
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md

nothing added to commit but untracked files present (use "git add" to track)
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

Git می‌گوید ‪README.md‬ یک فایل «ردیابی‌نشده» (untracked) است؛ یعنی Git از وجودش باخبر است، اما هنوز هیچ تاریخچه‌ای برایش ثبت نکرده. توصیه‌ی خیلی خوبی که همین‌جا باید بدهیم: به عادت اجرای مکرر ‪git status‬ عادت کنید، به‌خصوص پیش و پس از هر عملیات مهم. این دستور، دقیقاً و بی‌غل‌وغش، به شما می‌گوید Git در همین لحظه چه چیزی می‌بیند.

### ۲.۳ مرحله‌بندی تغییرات با ‪git add‬

برای این‌که به Git بگویید این فایل را برای کامیت بعدی آماده کنید (یعنی از درخت کاری به ناحیه‌ی مرحله‌بندی منتقلش کنید):

</div>

<div style="text-align:left;">

```
$ git add README.md
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر بخواهید *همه‌ی* فایل‌های تغییریافته و تازه در پوشه‌ی فعلی (و زیرپوشه‌هایش) را یک‌جا مرحله‌بندی کنید:

</div>

<div style="text-align:left;">

```
$ git add .
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

چند حالت دیگر هم برای این دستور رایج هستند:

- ‪git add -A‬: همه‌ی فایل‌های تغییریافته در *کل* مخزن را مرحله‌بندی می‌کند (نه فقط پوشه‌ی فعلی).
- ‪git add -u‬: فقط فایل‌های *از‌قبل‌ردیابی‌شده* که تغییر کرده‌اند را مرحله‌بندی می‌کند؛ فایل‌های کاملاً تازه را نادیده می‌گیرد.
- ‪git add -p‬: به‌صورت تعاملی، هر تکه تغییر (hunk) را جداگانه به شما نشان می‌دهد و می‌پرسد آیا همان تکه را مرحله‌بندی کنید یا نه؛ برای وقتی که فقط بخشی از تغییرات یک فایل را می‌خواهید کامیت کنید، بسیار مفید است.

دوباره وضعیت را بررسی کنید:

</div>

<div style="text-align:left;">

```
$ git status
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

</div>

<div style="text-align:left;">

```
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

حالا ‪README.md‬ در ناحیه‌ی مرحله‌بندی است و آماده‌ی کامیت شدن.

### ۲.۴ ثبت اولین کامیت

برای ذخیره‌ی دائمی این عکس فوری در تاریخچه‌ی مخزن:

</div>

<div style="text-align:left;">

```
$ git commit -m "Initial commit"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

فلگ ‪-m‬ به شما اجازه می‌دهد پیام کامیت را مستقیماً در همان خط بنویسید؛ اگر این فلگ را ننویسید، Git ویرایشگر متن پیش‌فرضتان (که در فصل ۱ تنظیم کردیم) را باز می‌کند تا پیام را آن‌جا بنویسید. خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
[main (root-commit) a1b2c3d] Initial commit
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### نوشتن پیام کامیت خوب

طبق راهنمای رسمی Git، بهترین شیوه این است که پیام کامیت با یک خط کوتاه (حداکثر ۵۰ کاراکتر) که خلاصه‌ی تغییر را می‌گوید شروع شود، سپس یک خط خالی، و بعد از آن، توضیح مفصل‌تر بیاید. برای نوشتن پیام چندخطی، کافی است ‪-m‬ را ننویسید تا ویرایشگر باز شود، یا از چند فلگ ‪-m‬ پشت‌سرهم استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git commit -m "Add user authentication" -m "Implements login and logout endpoints using JWT tokens for session management."
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### کامیت مستقیم فایل‌های ردیابی‌شده با ‪-a‬

اگر فقط فایل‌های *از‌قبل‌ردیابی‌شده* را تغییر داده‌اید (نه فایل‌های کاملاً تازه) و می‌خواهید مرحله‌بندی و کامیت را در یک قدم انجام دهید:

</div>

<div style="text-align:left;">

```
$ git commit -am "Fix typo in README"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این میان‌بر، معادل اجرای ‪git add -u‬ و بلافاصله ‪git commit‬ است، اما همان‌طور که گفتیم، فایل‌های *تازه* را شامل نمی‌شود؛ برای آن‌ها همچنان باید صریحاً ‪git add‬ بزنید.

### ۲.۵ دیدن تفاوت‌ها با ‪git diff‬

پیش از کامیت کردن، معمولاً می‌خواهید دقیقاً ببینید چه چیزی تغییر کرده. بیایید فایل ‪README.md‬ را ویرایش کنیم:

</div>

<div style="text-align:left;">

```
$ echo "This project does something cool." >> README.md
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برای دیدن تفاوت‌های *مرحله‌بندی‌نشده* (یعنی چیزی که در درخت کاری تغییر کرده اما هنوز ‪git add‬ نشده):

</div>

<div style="text-align:left;">

```
$ git diff
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی به فرمت یکپارچه‌ی آشنایی که در diff استاندارد یونیکس هم می‌بینید نمایش داده می‌شود:

</div>

<div style="text-align:left;">

```
diff --git a/README.md b/README.md
index 9daeafb..b3f9d17 100644
--- a/README.md
+++ b/README.md
@@ -1 +1,2 @@
 # My Project
+This project does something cool.
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

پس از ‪git add README.md‬، اگر دوباره ‪git diff‬ بزنید، دیگر چیزی نمی‌بینید، چون آن تغییرات به ناحیه‌ی مرحله‌بندی منتقل شده‌اند. برای دیدن تفاوت‌های *مرحله‌بندی‌شده* (چیزی که آماده‌ی کامیت است)، از ‪--staged‬ (یا معادل قدیمی‌ترش، ‪--cached‬) استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git diff --staged
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">
اگر با دستور diff آشنایی ندارید پیشنهاد می‌کنم از طریق لینک زیر به راهنمای فارسی diff مراجعه کنید و آن را بخوانید.

[مطالعه راهنمای استفاده دستور diff](https://github.com/mehmetlotfi/farsi-manual/tree/main/diff)


</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۲.۶ بررسی تاریخچه با ‪git log‬

برای دیدن فهرست همه‌ی کامیت‌های ثبت‌شده:

</div>

<div style="text-align:left;">

```
$ git log
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
commit b3f9d17e5a8c2b1f4d6e8a0c2e4f6a8c0e2f4a6c
Author: Mehmet Lotfi <mehmet.lotfi@gmail.com>
Date:   Thu Jan 15 10:30:00 2026 +0330

    Add project description

commit a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0

Date:   Thu Jan 15 10:15:00 2026 +0330

    Initial commit
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

چند نسخه‌ی کوتاه‌تر و کاربردی‌تر از ‪log‬ که در کار روزمره بسیار به کار می‌آیند:

</div>

<div style="text-align:left;">

```
$ git log --oneline
$ git log --stat
$ git log -p
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

‪--oneline‬ هر کامیت را در یک خط خلاصه می‌کند، ‪--stat‬ خلاصه‌ای از فایل‌های تغییریافته در هر کامیت نشان می‌دهد، و ‪-p‬ تفاوت کامل هر کامیت را هم نمایش می‌دهد. در فصل ۷، به‌طور کامل و عمیق‌تر به گزینه‌های پیشرفته‌ی ‪log‬ می‌پردازیم.

### ۲.۷ حذف و جابه‌جایی فایل‌ها

برای حذف یک فایل، هم از دیسک و هم از ردیابی Git:

</div>

<div style="text-align:left;">

```
$ git rm old-file.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر می‌خواهید فایل روی دیسک باقی بماند، اما Git دیگر آن را ردیابی نکند (مثلاً فایلی که اشتباهاً کامیت شده بود):

</div>

<div style="text-align:left;">

```
$ git rm --cached secret-config.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برای تغییر نام یا جابه‌جایی یک فایل:

</div>

<div style="text-align:left;">

```
$ git mv old-name.txt new-name.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نکته‌ی مفهومی جالب اینجاست: Git، برخلاف بسیاری از سیستم‌های دیگر، تغییر نام فایل را به‌طور مستقیم *ردیابی* نمی‌کند. دستور ‪git mv‬ فقط یک میان‌بر راحت است که در پس‌زمینه، حذف فایل قدیمی و افزودن فایل جدید را انجام می‌دهد؛ Git بعداً، هنگام نمایش تاریخچه، با مقایسه‌ی محتوای فایل‌های حذف‌شده و اضافه‌شده، خودش تشخیص می‌دهد که احتمالاً یک تغییر نام رخ داده است.

### ۲.۸ نادیده گرفتن فایل‌ها با ‪.gitignore‬

در هر پروژه‌ی واقعی، معمولاً فایل‌هایی هستند که اصلاً نمی‌خواهید Git آن‌ها را ردیابی کند: فایل‌های موقت، پوشه‌ی وابستگی‌ها (مثل ‪node_modules‬)، فایل‌های پیکربندی محیطی حاوی رمز، یا خروجی‌های کامپایل‌شده. برای این کار، فایلی به نام ‪.gitignore‬ در ریشه‌ی مخزن بسازید:

</div>

<div style="text-align:left;">

```
$ cat > .gitignore << 'EOF'
node_modules/
*.log
.env
__pycache__/
*.pyc
.DS_Store
EOF
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

از این پس، Git به‌طور خودکار هر فایل یا پوشه‌ای که با این الگوها مطابقت داشته باشد را در ‪git status‬ و ‪git add .‬ نادیده می‌گیرد. خود فایل ‪.gitignore‬ را هم باید کامیت کنید تا بقیه‌ی همکارانتان هم از همان قوانین پیروی کنند:

</div>

<div style="text-align:left;">

```
$ git add .gitignore
$ git commit -m "Add .gitignore"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نکته‌ی مهم: ‪.gitignore‬ فقط روی فایل‌های *هنوز ردیابی‌نشده* اثر دارد. اگر فایلی قبلاً کامیت شده و بعداً آن را به ‪.gitignore‬ اضافه کنید، Git همچنان به ردیابی‌اش ادامه می‌دهد. برای متوقف کردن ردیابی یک فایل که قبلاً کامیت شده، باید صریحاً از همان دستور بخش قبل استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git rm --cached config/secrets.yml
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۲.۹ یک نکته‌ی کلیدی: Git محتوا را ردیابی می‌کند

به یاد بیاورید که در فصل قبل گفتیم Git از یک دستور واحد، یعنی ‪git add‬، هم برای فایل‌های تازه و هم برای فایل‌های تغییریافته استفاده می‌کند. حالا که این دستور را عملاً به کار بردید، این مفهوم باید کاملاً واضح شده باشد: هر بار که ‪git add‬ می‌زنید، دارید می‌گویید «این *محتوای فعلی* این فایل را، همین حالا، عکس بگیر»؛ اگر بعد از آن، فایل را دوباره تغییر دهید، باید دوباره ‪git add‬ بزنید تا آن تغییر تازه هم دیده شود؛ کامیت قبلی تغییرات جدید را خودش به‌خودی به‌روزرسانی نمی‌کند.

### ۲.۱۰ خلاصه‌ی چرخه‌ی کامل

بیایید کل چرخه‌ای که در این فصل یاد گرفتیم را یک‌جا مرور کنیم؛ این همان روالی است که در کار روزمره با Git، بارها و بارها تکرار می‌کنید:

</div>

<div style="text-align:left;">

```
$ echo "print('Hello, Git!')" > app.py
$ git status
$ git add app.py
$ git diff --staged
$ git commit -m "Add hello world script"
$ git log --oneline
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

تغییر بدهید، وضعیت را بررسی کنید، مرحله‌بندی کنید، تفاوت را دوباره چک کنید، کامیت کنید، و تاریخچه را مرور کنید؛ این پنج قدم، ستون فقرات تمام کارهایی هستند که در فصل‌های بعدی، روی آن‌ها بنا می‌کنیم.

### ۲.۱۱ حالا چه؟

در این فصل، اولین مخزن خود را ساختید و چرخه‌ی کامل کار با Git، از ساختن فایل تا کامیت کردن و بررسی تاریخچه، را قدم‌به‌قدم تمرین کردید. همچنین یاد گرفتید چگونه فایل‌ها را حذف یا جابه‌جا کنید و با ‪.gitignore‬ فایل‌های ناخواسته را از ردیابی کنار بگذارید.

تا این‌جا، همیشه روی یک خط زمانی واحد کار کردیم. اما یکی از بزرگ‌ترین قدرت‌های Git، توانایی کار روی چند نسخه‌ی موازی از پروژه، بدون تداخل با یکدیگر، است. در فصل بعد، وارد دنیای شاخه‌بندی (branching) می‌شویم.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| git init | یک پوشه‌ی موجود را به یک مخزن تازه‌ی Git تبدیل می‌کند. |
| git status | وضعیت فعلی فایل‌های ردیابی‌شده، تغییریافته، و مرحله‌بندی‌شده را نمایش می‌دهد. |
| git add FILE یا git add . | فایل مشخص یا همه‌ی فایل‌های تغییریافته را مرحله‌بندی می‌کند. |
| git add -p | تغییرات را تکه‌به‌تکه و به‌صورت تعاملی مرحله‌بندی می‌کند. |
| git commit -m "MSG" | محتوای مرحله‌بندی‌شده را با پیام مشخص، به‌طور دائمی کامیت می‌کند. |
| git commit -am "MSG" | فایل‌های از‌قبل‌ردیابی‌شده‌ی تغییریافته را مرحله‌بندی و کامیت می‌کند. |
| git diff | تفاوت‌های مرحله‌بندی‌نشده‌ی درخت کاری را نمایش می‌دهد. |
| git diff --staged | تفاوت‌های مرحله‌بندی‌شده و آماده‌ی کامیت را نمایش می‌دهد. |
| git log / --oneline / --stat / -p | تاریخچه‌ی کامیت‌ها را، با سطوح مختلف جزئیات، نمایش می‌دهد. |
| git rm FILE | فایل را هم از دیسک و هم از ردیابی Git حذف می‌کند. |
| git rm --cached FILE | فایل را فقط از ردیابی Git حذف می‌کند، روی دیسک باقی می‌ماند. |
| git mv OLD NEW | نام فایل را تغییر داده و تغییر را مرحله‌بندی می‌کند. |
| .gitignore | فایلی که الگوهای فایل‌های نادیده‌گرفته‌شده توسط Git را مشخص می‌کند. |

</div>

## فصل ۳

### <u>شاخه‌بندی و ادغام</u>

در فصل قبل، همیشه روی یک خط زمانی واحد کار کردیم. اما یکی از بزرگ‌ترین قدرت‌های Git، که آن را به این‌همه محبوب تبدیل کرده، توانایی ساختن نسخه‌های موازی و مستقل از یک پروژه است؛ به این نسخه‌های موازی، «شاخه» (branch) گفته می‌شود. در این فصل، یاد می‌گیرید چگونه شاخه بسازید، بین آن‌ها جابه‌جا شوید، و در نهایت، تغییرات آن‌ها را دوباره با هم ادغام (merge) کنید، به‌همراه نحوه‌ی تشخیص و رفع تعارض‌هایی که گاهی در این مسیر پیش می‌آیند.

### ۳.۱ شاخه چیست، مفهومی

یک شاخه، در واقع چیزی نیست جز یک اشاره‌گر متحرک به یک کامیت مشخص. وقتی روی یک شاخه کامیت تازه‌ای می‌سازید، آن اشاره‌گر به‌طور خودکار جلو می‌رود تا به آخرین کامیت اشاره کند. این سبکی بودن شاخه‌ها (که فقط یک اشاره‌گر کوچک هستند، نه یک کپی کامل از کل پروژه) دقیقاً همان چیزی است که مستندات رسمی Git هم به آن اشاره می‌کنند: «شاخه‌ها ارزان و ساده‌اند، پس این روش خوبی برای امتحان کردن چیزهای تازه است.»

### ۳.۲ ساختن و دیدن شاخه‌ها

برای ساختن یک شاخه‌ی تازه به نام ‪experimental‬:

</div>

<div style="text-align:left;">

```
$ git branch experimental
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برای دیدن فهرست همه‌ی شاخه‌های موجود:

</div>

<div style="text-align:left;">

```
$ git branch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
  experimental
* main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

علامت ستاره (‪*‬) نشان می‌دهد شما در حال حاضر روی کدام شاخه هستید. توجه کنید که فقط با ‪git branch experimental‬، شاخه‌ی تازه ساخته شده، اما هنوز به آن *سوییچ* نکرده‌اید؛ همچنان روی ‪main‬ هستید.

### ۳.۳ جابه‌جایی بین شاخه‌ها

برای سوییچ کردن به شاخه‌ی تازه، از دستور ‪git switch‬ استفاده می‌کنیم (که در نسخه‌های جدیدتر Git معرفی شده تا نقش دوگانه‌ی دستور قدیمی‌تر ‪git checkout‬ را ساده‌تر کند):

</div>

<div style="text-align:left;">

```
$ git switch experimental
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا با روش قدیمی‌تر و همچنان کاملاً معتبر:

</div>

<div style="text-align:left;">

```
$ git checkout experimental
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یک میان‌بر بسیار کاربردی، ساختن شاخه *و* سوییچ کردن به آن، هر دو در یک دستور:

</div>

<div style="text-align:left;">

```
$ git switch -c new-feature
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

(یا معادل قدیمی‌ترش، ‪git checkout -b new-feature‬)

بیایید کمی روی شاخه‌ی ‪experimental‬ کار کنیم:

</div>

<div style="text-align:left;">

```
$ echo "Experimental feature" >> README.md
$ git commit -am "Add experimental note"
$ git switch main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر حالا محتوای ‪README.md‬ را ببینید، آن خط تازه را نمی‌بینید؛ چون آن تغییر فقط روی شاخه‌ی ‪experimental‬ ثبت شده، نه روی ‪main‬. این دقیقاً همان جداسازی موازی است که شاخه‌ها فراهم می‌کنند.

### ۳.۴ ادغام (Merge) دو شاخه

فرض کنید ویژگی روی شاخه‌ی ‪experimental‬ را تکمیل کرده‌اید و حالا می‌خواهید آن را با ‪main‬ ترکیب کنید. مرحله‌ی اول این است که مطمئن شوید روی شاخه‌ای هستید که می‌خواهید تغییرات *به آن* اضافه شوند (اصطلاحاً «شاخه‌ی دریافت‌کننده»):

</div>

<div style="text-align:left;">

```
$ git switch main
$ git merge experimental
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

Git، بسته به وضعیت دو شاخه، یکی از دو نوع ادغام را انجام می‌دهد.

### ادغام Fast-Forward

اگر از زمان انشعاب شاخه‌ی ‪experimental‬ از ‪main‬، هیچ کامیت تازه‌ای *روی خود ‪main‬* ثبت نشده باشد، Git می‌تواند به سادگی اشاره‌گر ‪main‬ را جلو ببرد تا دقیقاً به همان‌جایی برسد که ‪experimental‬ رسیده است. به این کار «ادغام تندروانه» یا Fast-Forward می‌گویند، چون هیچ کامیت جدیدی ساخته نمی‌شود؛ فقط یک اشاره‌گر جابه‌جا می‌شود:

</div>

<div style="text-align:left;">

```
Updating a1b2c3d..b3f9d17
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ادغام سه‌طرفه (Three-Way Merge)

اما اگر هر دو شاخه، *از زمان انشعاب*، کامیت‌های تازه‌ی خودشان را داشته باشند (یعنی تاریخچه‌شان واقعاً از هم «منشعب» شده)، Git نمی‌تواند به‌سادگی یک اشاره‌گر را جلو ببرد. در عوض، یک «کامیت ادغام» (merge commit) تازه می‌سازد که *دو* والد دارد: یکی از هر شاخه. به این کار «ادغام سه‌طرفه» می‌گویند، چون Git برای انجامش، سه نسخه را با هم مقایسه می‌کند: آخرین کامیت هر یک از دو شاخه، و آخرین نقطه‌ی مشترک بین آن‌ها (که به آن merge base گفته می‌شود).

اگر تغییرات دو شاخه با هم تداخلی نداشته باشند، Git این ادغام سه‌طرفه را کاملاً خودکار انجام می‌دهد و از شما فقط یک پیام کامیت (که از قبل پر شده) تأیید می‌گیرد.

### اجبار به ساختن کامیت ادغام با ‪--no-ff‬

اگر می‌خواهید حتی در شرایطی که یک ادغام Fast-Forward ممکن است، همیشه یک کامیت ادغام واقعی ساخته شود (که برخی تیم‌ها ترجیح می‌دهند، چون تاریخچه‌ی روشن‌تری از این‌که «این شاخه، این‌جا وارد شد» نشان می‌دهد)، از فلگ ‪--no-ff‬ استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git merge --no-ff experimental
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۳.۵ تعارض ادغام (Merge Conflict) و نحوه‌ی رفع آن

تعارض زمانی رخ می‌دهد که هر دو شاخه، *همان بخش* از یک فایل را به دو شکل متفاوت تغییر داده باشند؛ Git نمی‌داند کدام نسخه درست است و از شما کمک می‌خواهد. بیایید یک سناریوی تعارض بسازیم. فرض کنید هر دو شاخه، خط اول یک فایل پیکربندی را تغییر داده‌اند:

</div>

<div style="text-align:left;">

```
$ git merge feature-branch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر تعارض رخ دهد، خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
Automatic merge failed; fix conflicts and then commit the result.
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر ‪git status‬ بزنید، فایل مشکل‌دار را با وضعیت «both modified» می‌بینید. حالا فایل ‪config.txt‬ را باز کنید؛ محتوایش چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
<<<<<<< HEAD
region = "eu-west"
=======
region = "us-east"
>>>>>>> feature-branch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این نشانه‌ها را باید بشناسید: هرچیزی *بین* ‪<<<<<<< HEAD‬ و ‪=======‬ نسخه‌ی شاخه‌ی فعلی شماست (که «ours» هم نامیده می‌شود)، و هرچیزی *بین* ‪=======‬ و ‪>>>>>>> feature-branch‬ نسخه‌ی شاخه‌ای است که در حال ادغام کردنش هستید («theirs»). کار شما این است که این بخش را ویرایش کنید، هر نشانه (‪<<<<<<<‬، ‪=======‬، ‪>>>>>>>‬) را کاملاً حذف کنید، و نسخه‌ی نهایی درست را بنویسید:

</div>

<div style="text-align:left;">

```
region = "eu-west"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

سپس فایل حل‌شده را مرحله‌بندی و کامیت کنید تا ادغام تکمیل شود:

</div>

<div style="text-align:left;">

```
$ git add config.txt
$ git commit
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نکته‌ی کاربردی: اگر می‌خواهید کل نسخه‌ی شاخه‌ی فعلی خود را نگه دارید (بدون ویرایش دستی):

</div>

<div style="text-align:left;">

```
$ git checkout --ours config.txt
$ git add config.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا اگر می‌خواهید کل نسخه‌ی شاخه‌ی دیگر را بپذیرید:

</div>

<div style="text-align:left;">

```
$ git checkout --theirs config.txt
$ git add config.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### لغو کامل یک ادغام مشکل‌دار

اگر در وسط حل تعارض متوجه شدید کارها خراب شده و ترجیح می‌دهید از اول شروع کنید، Git راه فراری دارد که دقیقاً همه‌چیز را به وضعیت پیش از شروع ادغام برمی‌گرداند:

</div>

<div style="text-align:left;">

```
$ git merge --abort
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۳.۶ حذف یک شاخه

پس از این‌که یک شاخه با موفقیت ادغام شد و دیگر نیازی به آن نیست، می‌توانید آن را حذف کنید:

</div>

<div style="text-align:left;">

```
$ git branch -d experimental
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

حرف کوچک ‪-d‬ یک بررسی ایمنی انجام می‌دهد: فقط اگر آن شاخه *قبلاً کاملاً ادغام شده باشد* اجازه‌ی حذف می‌دهد. اگر بخواهید یک شاخه را، حتی اگر هنوز ادغام نشده (مثلاً چون تصمیم گرفتید یک ایده را کنار بگذارید)، به‌زور حذف کنید، از حرف بزرگ استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git branch -D crazy-idea
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

همان‌طور که در مستندات رسمی هم آمده، همین سبکی و ارزانی شاخه‌هاست که آن‌ها را به ابزار ایده‌آلی برای امتحان کردن ایده‌های جدید تبدیل می‌کند؛ اگر ایده جواب نداد، فقط شاخه را با ‪-D‬ حذف کنید و هیچ ردی از آن باقی نمی‌ماند.

### ۳.۷ حالا چه؟

در این فصل، مفهوم شاخه به‌عنوان یک اشاره‌گر متحرک را یاد گرفتید، بین شاخه‌ها جابه‌جا شدید، و دو نوع ادغام، یعنی Fast-Forward و سه‌طرفه، را با نمودارهای بصری دیدید. همچنین یاد گرفتید چگونه تعارض‌های ادغام را تشخیص دهید و به‌درستی رفع کنید.

ادغام (merge) تنها روشی نیست که Git برای ترکیب تاریخچه‌ی دو شاخه در اختیار شما می‌گذارد. در فصل بعد، با روش دیگری به نام rebase آشنا می‌شوید که، به‌جای ساختن یک کامیت ادغام جداگانه، تاریخچه‌ی شما را به شکلی کاملاً خطی و اغلب خواناتر بازمی‌نویسد.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| git branch | فهرست شاخه‌های موجود را نمایش می‌دهد؛ شاخه‌ی فعلی با ستاره مشخص می‌شود. |
| git branch NAME | یک شاخه‌ی تازه می‌سازد، بدون سوییچ کردن به آن. |
| git switch NAME یا git checkout NAME | به شاخه‌ی مشخص‌شده سوییچ می‌کند. |
| git switch -c NAME یا git checkout -b NAME | یک شاخه‌ی تازه می‌سازد و بلافاصله به آن سوییچ می‌کند. |
| git merge BRANCH | تغییرات شاخه‌ی مشخص‌شده را در شاخه‌ی فعلی ادغام می‌کند. |
| git merge --no-ff BRANCH | همیشه یک کامیت ادغام واقعی می‌سازد، حتی اگر Fast-Forward ممکن باشد. |
| git merge --abort | یک ادغام در حال انجام (مثلاً به دلیل تعارض) را کاملاً لغو می‌کند. |
| git checkout --ours FILE | در حین تعارض، نسخه‌ی شاخه‌ی فعلی فایل را انتخاب می‌کند. |
| git checkout --theirs FILE | در حین تعارض، نسخه‌ی شاخه‌ی درحال‌ادغام فایل را انتخاب می‌کند. |
| git branch -d NAME | یک شاخه‌ی کاملاً ادغام‌شده را حذف می‌کند. |
| git branch -D NAME | یک شاخه را، حتی اگر ادغام نشده، به‌زور حذف می‌کند. |

</div>

## فصل ۴

### <u>Rebase و تاریخچه‌ی تمیز</u>

در فصل قبل، با ادغام (merge) آشنا شدیم که تاریخچه‌ی دو شاخه‌ی منشعب را با ساختن یک کامیت ادغام ترکیب می‌کند. در این فصل، با روش دیگری آشنا می‌شوید که هدف کاملاً متفاوتی دارد: نه ترکیب دو تاریخچه در کنار هم، بلکه *بازنویسی* کامیت‌های شما، طوری‌که انگار از همان ابتدا، روی نسخه‌ی جدیدترِ شاخه‌ی دیگر ساخته شده‌اند. این روش، ‪git rebase‬ نام دارد و یکی از قدرتمندترین، و در عین حال خطرناک‌ترین، ابزارهای Git است.

### ۴.۱ Rebase چیست، مفهومی

فرض کنید روی شاخه‌ی ‪feature‬ کار می‌کنید، و در همین حین، همکارانتان چند کامیت تازه به ‪main‬ اضافه کرده‌اند. حالا دو شاخه از هم منشعب شده‌اند. در فصل قبل دیدیم راه‌حل ادغام این است که یک کامیت ادغام تازه بسازیم که هر دو تاریخچه را به هم وصل کند. اما ‪rebase‬ رویکرد کاملاً متفاوتی دارد: کامیت‌های *شما* را موقتاً کنار می‌گذارد، شاخه‌ی شما را دقیقاً به آخرین نقطه‌ی ‪main‬ می‌برد، و سپس کامیت‌های شما را، یکی‌یکی، دوباره روی همان نقطه‌ی جدید «بازپخش» (replay) می‌کند.

نتیجه‌ی نهایی، یک تاریخچه‌ی کاملاً *خطی* است؛ انگار از همان ابتدا، شما کار خود را دقیقاً بعد از آخرین کامیت ‪main‬ شروع کرده بودید، نه از یک نقطه‌ی قدیمی‌تر. نمودار زیر این تفاوت را به‌روشنی نشان می‌دهد:

نکته‌ی بسیار مهمی که در این نمودار مشخص است: کامیت‌های بازپخش‌شده در حالت rebase، هرچند محتوایشان یکسان است، شناسه‌ی (hash) کاملاً متفاوتی نسبت به کامیت‌های اصلی دارند. این یعنی، از دید Git، این‌ها کامیت‌های *تازه‌ای* هستند، نه همان کامیت‌های قبلی که فقط جابه‌جا شده باشند. دقیقاً همین نکته، پایه‌ی مهم‌ترین قانونی است که در بخش ۴.۴ همین فصل با جزئیات کامل توضیح می‌دهیم.

### ۴.۲ استفاده‌ی پایه از rebase

بیایید یک سناریوی عملی ببینیم. فرض کنید روی شاخه‌ی ‪feature‬ هستید و می‌خواهید آخرین تغییرات ‪main‬ را در شاخه‌ی خودتان بیاورید، اما به‌جای ادغام، می‌خواهید تاریخچه‌ی خطی داشته باشید:

</div>

<div style="text-align:left;">

```
$ git switch feature
$ git rebase main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر همه‌چیز بدون تعارض پیش برود، خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
Successfully rebased and updated refs/heads/feature.
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

از این لحظه، شاخه‌ی ‪feature‬ شما انگار از همان آخرین نقطه‌ی ‪main‬ شروع شده است. اگر بعداً بخواهید این شاخه را با ‪main‬ ادغام کنید، چون تاریخچه دیگر منشعب نیست، Git می‌تواند از یک ادغام ساده‌ی Fast-Forward (که در فصل قبل دیدیم) استفاده کند، و هیچ کامیت ادغام اضافه‌ای در تاریخچه ثبت نمی‌شود.

### رفع تعارض هنگام rebase

اگر در حین بازپخش کامیت‌ها، Git به تعارضی برخورد کند، فرایند متوقف می‌شود:

</div>

<div style="text-align:left;">

```
CONFLICT (content): Merge conflict in config.txt
error: could not apply a1b2c3d... Update config settings
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

روش رفع آن، دقیقاً مثل رفع تعارض ادغام در فصل قبل است: فایل را باز کنید، نشانه‌های ‪<<<<<<<‬، ‪=======‬، و ‪>>>>>>>‬ را پیدا کنید، تصمیم بگیرید نسخه‌ی نهایی چه باید باشد، و نشانه‌ها را حذف کنید. اما به‌جای ‪git commit‬، این‌بار باید به Git بگویید ادامه بده:

</div>

<div style="text-align:left;">

```
$ git add config.txt
$ git rebase --continue
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر با کامیت بعدی هم به تعارض دیگری برخوردید، همین چرخه را تکرار می‌کنید. اگر در هر لحظه بخواهید کل عملیات را لغو کنید و به وضعیت قبل از شروع rebase برگردید:

</div>

<div style="text-align:left;">

```
$ git rebase --abort
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۴.۳ Rebase تعاملی: مرتب کردن تاریخچه‌ی خودتان

قدرتمندترین کاربرد rebase، حالت *تعاملی* آن است که به شما اجازه می‌دهد پیش از اشتراک‌گذاری کارتان با دیگران، تاریخچه‌ی محلی خودتان را کاملاً ویرایش کنید: کامیت‌ها را ترکیب کنید، پیام‌هایشان را بازنویسی کنید، ترتیبشان را عوض کنید، یا حتی بعضی را کاملاً حذف کنید.

فرض کنید در حین کار روی یک ویژگی، این کامیت‌های نه‌چندان مرتب را ساخته‌اید:

</div>

<div style="text-align:left;">

```
$ git log --oneline
```
</div>

<div style="text-align:left;">

```
b1c2d3e Add payment API endpoint
7890abc Fix typo in payment model
d4e5f6a WIP: forgot to add migration
a1b2c3d Add payment model
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برای مرتب کردن این چهار کامیت پیش از ادغام یا فرستادنشان به دیگران، rebase تعاملی روی چهار کامیت اخیر را اجرا می‌کنید:

</div>

<div style="text-align:left;">

```
$ git rebase -i HEAD~4
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

Git ویرایشگر متن پیش‌فرضتان را باز می‌کند و فهرستی مثل این نشان می‌دهد:

</div>

<div style="text-align:left;">

```
pick a1b2c3d Add payment model
pick d4e5f6a WIP: forgot to add migration
pick 7890abc Fix typo in payment model
pick b1c2d3e Add payment API endpoint
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

با تغییر کلمه‌ی ‪pick‬ در ابتدای هر خط، به Git می‌گویید با آن کامیت چه کار کند. مهم‌ترین دستورها عبارت‌اند از:

- ‪pick‬: کامیت را همان‌طور که هست نگه دار.
- ‪reword‬: کامیت را نگه دار، اما اجازه بده پیامش را ویرایش کنم.
- ‪squash‬: این کامیت را در کامیت *قبلی* (خطی که بالای آن است) ادغام کن، و اجازه بده هر دو پیام را با هم ویرایش کنم.
- ‪fixup‬: مثل ‪squash‬، اما پیام این کامیت را کاملاً دور بینداز.
- ‪drop‬: این کامیت را کاملاً حذف کن.

برای مثال، برای ترکیب دو کامیت میانی (که فقط رفع اشکال کامیت اول بودند) در کامیت اول، فایل را این‌طور تغییر می‌دهیم:

</div>

<div style="text-align:left;">

```
pick a1b2c3d Add payment model
fixup d4e5f6a WIP: forgot to add migration
fixup 7890abc Fix typo in payment model
pick b1c2d3e Add payment API endpoint
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

پس از ذخیره و بستن ویرایشگر، Git این دستورها را اجرا می‌کند، و تاریخچه‌ی نهایی، دو کامیت تمیز و معنادار خواهد داشت، به‌جای چهار کامیت درهم و پر از «WIP» و «Fix typo». به قول یکی از راهنماهای معتبر Atlassian، از دید هرکس دیگری که به این تاریخچه نگاه کند، انگار شما از همان ابتدا، دقیقاً با همین دو کامیت منظم کار کرده‌اید.

### ۴.۴ قانون طلایی Rebase

حالا به مهم‌ترین نکته‌ی این فصل می‌رسیم، نکته‌ای که تقریباً هر منبع معتبری درباره‌ی Git به آن اشاره می‌کند: هرگز کامیت‌هایی را که قبلاً به یک شاخه‌ی مشترک و عمومی فرستاده‌اید (push کرده‌اید) و احتمال دارد دیگران هم آن‌ها را گرفته (pull کرده) باشند، rebase نکنید.

دلیلش دقیقاً همان چیزی است که در بخش ۴.۱ دیدیم: rebase، کامیت‌های قدیمی را با کامیت‌های *تازه و متفاوت* (با شناسه‌ی جدید) جایگزین می‌کند. اگر همکار شما قبلاً نسخه‌ی قدیمی این کامیت‌ها را گرفته باشد، و شما تاریخچه را rebase کرده و دوباره push کنید، از دید Git او، انگار دو تاریخچه‌ی کاملاً متفاوت وجود دارد؛ این وضعیت باعث سردرگمی شدید، تعارض‌های عجیب، و در بدترین حالت، از دست رفتن کار می‌شود.

قانون عملی و ساده این است: rebase را فقط روی شاخه‌های محلی و خصوصی خودتان، پیش از اشتراک‌گذاری، استفاده کنید. اگر شاخه‌ای هنوز فقط پیش خودتان است (هیچ‌کس دیگری آن را pull نکرده)، rebase کاملاً امن است. به محض این‌که آن را push کردید و دیگران احتمالاً به آن دسترسی پیدا کرده‌اند، فرض کنید آن تاریخچه دیگر «عمومی» است و دیگر نباید بازنویسی‌اش کنید.

### ۴.۵ Cherry-Pick: کپی کردن یک کامیت مشخص

ابزار دیگری که در همین خانواده قرار می‌گیرد، ‪git cherry-pick‬ است. این دستور، به‌جای بازپخش *همه‌ی* کامیت‌های یک شاخه (کاری که rebase انجام می‌دهد)، فقط *یک* کامیت مشخص را از هر جای دیگری از تاریخچه گرفته و آن را روی شاخه‌ی فعلی شما اعمال می‌کند:

</div>

<div style="text-align:left;">

```
$ git cherry-pick a1b2c3d
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این ابزار به‌خصوص برای موقعیت‌هایی مفید است که یک رفع اشکال حیاتی (hotfix) روی یک شاخه ساخته شده، و می‌خواهید همان *یک* تغییر، بدون آوردن بقیه‌ی کارهای ناتمام آن شاخه، به شاخه‌ی دیگری (مثلاً یک نسخه‌ی پایدار قدیمی‌تر که هنوز پشتیبانی می‌شود) هم اعمال شود.

### ۴.۶ مقایسه‌ی نهایی: کِی از کدام استفاده کنیم

| ابزار | چه کاری می‌کند | بهترین کاربرد |
|---|---|---|
| merge | تاریخچه‌ی هر دو شاخه را حفظ می‌کند، یک کامیت ادغام می‌سازد | ادغام شاخه‌های مشترک و عمومی؛ حفظ ردپای دقیق تاریخچه |
| rebase | کامیت‌ها را با شناسه‌ی تازه، روی نقطه‌ی جدید بازپخش می‌کند | به‌روزرسانی یک شاخه‌ی *محلی* با آخرین تغییرات main |
| rebase -i | تاریخچه‌ی محلی را ویرایش، ترکیب، یا حذف می‌کند | تمیز کردن کامیت‌ها پیش از اشتراک‌گذاری یا Pull Request |
| cherry-pick | فقط یک کامیت مشخص را به شاخه‌ی دیگری کپی می‌کند | بردن یک رفع اشکال خاص به شاخه‌ای دیگر، بدون بقیه‌ی تاریخچه |

### ۴.۷ حالا چه؟

در این فصل، با rebase به‌عنوان روش دوم برای ترکیب تاریخچه‌ی شاخه‌ها آشنا شدید، دیدید چگونه با حالت تعاملی آن، تاریخچه‌ی خودتان را قبل از اشتراک‌گذاری تمیز کنید، و مهم‌تر از همه، «قانون طلایی» rebase را یاد گرفتید: هرگز تاریخچه‌ی عمومی و مشترک را بازنویسی نکنید.

تا این‌جا، همه‌ی کارمان روی مخزن *محلی* خودمان بوده است. اما Git واقعاً وقتی می‌درخشد که با دیگران همکاری کنید. در فصل بعد، وارد دنیای مخازن ریموت می‌شویم: چگونه یک مخزن را کلون کنید، تغییرات را با سرورهای راه دور مثل GitHub رد و بدل کنید، و با شاخه‌های ریموت کار کنید.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| git rebase BRANCH | کامیت‌های شاخه‌ی فعلی را روی آخرین نقطه‌ی BRANCH بازپخش می‌کند. |
| git rebase --continue | پس از رفع یک تعارض، ادامه‌ی فرایند rebase را انجام می‌دهد. |
| git rebase --abort | فرایند rebase را کاملاً لغو و به وضعیت پیش از شروع آن برمی‌گردد. |
| git rebase -i HEAD~N | rebase تعاملی روی N کامیت اخیر را باز می‌کند. |
| pick / reword / squash / fixup / drop | دستورهای قابل‌استفاده در فایل rebase تعاملی. |
| git cherry-pick HASH | یک کامیت مشخص را از هر جای تاریخچه به شاخه‌ی فعلی اعمال می‌کند. |

</div>

## فصل ۵

### <u>کار با مخازن ریموت</u>

تا این‌جا، همه‌ی کاری که انجام دادیم، منحصراً روی مخزن *محلی* خودمان بوده است. اما Git واقعاً وقتی می‌درخشد که با دیگران همکاری کنید. در این فصل، وارد دنیای مخازن ریموت (remote) می‌شویم: چگونه یک مخزن موجود را کلون کنید، چگونه یک مخزن محلی را به یک سرور راه دور مثل GitHub متصل کنید، و چگونه تغییرات را با دستورهای fetch، pull، و push رد و بدل کنید.

### ۵.۱ مخزن ریموت چیست

یک «ریموت» چیزی نیست جز نسخه‌ای از همان مخزن Git شما که در جای دیگری (معمولاً یک سرور، مثل GitHub یا GitLab) میزبانی می‌شود. به یاد بیاورید که در پیش‌گفتار گفتیم Git توزیع‌شده است: هر کپی از مخزن، چه روی کامپیوتر شما و چه روی سرور، شامل کل تاریخچه است. ریموت‌ها فقط نقاطی هستند که شما و همکارانتان، از طریق آن‌ها، تغییرات را با هم به اشتراک می‌گذارید.

### ۵.۲ کلون کردن یک مخزن موجود

اگر پروژه‌ای از قبل روی یک سرویس مثل GitHub وجود دارد و می‌خواهید یک نسخه‌ی کامل از آن، همراه با تمام تاریخچه‌اش، روی کامپیوتر خودتان داشته باشید، از ‪git clone‬ استفاده می‌کنید:

</div>

<div style="text-align:left;">

```
$ git clone https://github.com/example-user/example-project.git
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور یک پوشه‌ی تازه به نام ‪example-project‬ می‌سازد که شامل تمام فایل‌ها *و* تمام تاریخچه‌ی کامیت‌ها، شاخه‌ها، و تگ‌های آن پروژه است. نکته‌ی جالب: به‌طور خودکار، Git یک ریموت به نام ‪origin‬ می‌سازد که به همان آدرسی که کلون کرده‌اید اشاره می‌کند، و شاخه‌ی اصلی محلی شما (مثلاً ‪main‬) را طوری تنظیم می‌کند که این ریموت را «ردیابی» (track) کند؛ مفهومی که در بخش ۵.۵ همین فصل بیشتر توضیح می‌دهیم.

### ۵.۳ اتصال یک مخزن محلی موجود به یک ریموت

اگر برعکس این سناریو را دارید، یعنی از قبل یک مخزن محلی ساخته‌اید (با ‪git init‬، طبق فصل ۲) و می‌خواهید آن را به یک مخزن خالی تازه‌ساخته روی GitHub متصل کنید، از ‪git remote add‬ استفاده می‌کنید:

</div>

<div style="text-align:left;">

```
$ git remote add origin https://github.com/example-user/example-project.git
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نام ‪origin‬ فقط یک قرارداد رایج است (میان‌بری کوتاه به‌جای نوشتن کل URL هر بار)؛ می‌توانید هر اسمی که بخواهید انتخاب کنید، هرچند تقریباً همه‌ی توسعه‌دهندگان دنیا از همین ‪origin‬ برای ریموت اصلی استفاده می‌کنند.

برای دیدن فهرست ریموت‌های تنظیم‌شده و آدرس‌های متناظرشان:

</div>

<div style="text-align:left;">

```
$ git remote -v
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
origin  https://github.com/example-user/example-project.git (fetch)
origin  https://github.com/example-user/example-project.git (push)
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

همان‌طور که می‌بینید، یک ریموت می‌تواند دو URL جداگانه برای دریافت (fetch) و ارسال (push) داشته باشد؛ در حالت معمول این دو یکسان‌اند، اما در سناریوهای پیشرفته‌تر (مثل زمانی که می‌خواهید به دو سرویس میزبانی مختلف هم‌زمان push کنید)، می‌توان آن‌ها را جدا تنظیم کرد.

### ۵.۴ ارسال تغییرات با ‪git push‬

برای اولین‌بار که یک شاخه‌ی محلی را به یک ریموت می‌فرستید، باید مشخص کنید کدام ریموت و کدام شاخه، و به Git بگویید این ارتباط را به‌خاطر بسپارد:

</div>

<div style="text-align:left;">

```
$ git push -u origin main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

فلگ ‪-u‬ (مخفف ‪--set-upstream‬) به Git می‌گوید از این پس، شاخه‌ی محلی ‪main‬ را با شاخه‌ی ‪main‬ روی ‪origin‬ مرتبط (associate) کند. پس از این اولین بار، در دفعات بعدی، دیگر نیازی به نوشتن نام ریموت و شاخه نیست؛ کافی است بنویسید:

</div>

<div style="text-align:left;">

```
$ git push
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۵.۵ دریافت تغییرات: تفاوت میان ‪fetch‬ و ‪pull‬

این یکی از مهم‌ترین تفاوت‌های مفهومی است که هر کاربر Git باید کاملاً درک کند.

### ‪git fetch‬: فقط دانلود کن

دستور ‪git fetch‬ هر کامیت و شاخه‌ی تازه‌ای که روی ریموت وجود دارد را دانلود می‌کند و آن‌ها را در «شاخه‌های ردیابی ریموت» (remote-tracking branches)، مثل ‪origin/main‬، ذخیره می‌کند. اما این دستور، هیچ‌کدام از شاخه‌های محلی شما را تغییر نمی‌دهد.

</div>

<div style="text-align:left;">

```
$ git fetch origin
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

پس از این دستور، اگر ‪git log --oneline‬ روی شاخه‌ی ‪main‬ محلی خودتان بزنید، همچنان دقیقاً همان کامیت‌های قبلی را می‌بینید. برای دیدن آن‌چه *تازه* روی ریموت آمده، بدون این‌که هنوز چیزی را در کد خودتان ادغام کنید، می‌توانید این‌طور مقایسه کنید:

</div>

<div style="text-align:left;">

```
$ git log main..origin/main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این رفتار، دقیقاً همان چیزی است که ‪fetch‬ را ابزار امنی می‌کند: می‌توانید ببینید دیگران چه چیزی اضافه کرده‌اند، پیش از آن‌که تصمیم بگیرید آن را با کار خودتان ترکیب کنید.

### ‪git pull‬: دانلود کن و بلافاصله ادغام کن

دستور ‪git pull‬، همان‌طور که مستندات رسمی GitHub هم به‌صراحت می‌گویند، «یک میان‌بر راحت است که هم‌زمان ‪fetch‬ و ‪merge‬ را در یک دستور واحد انجام می‌دهد»:

</div>

<div style="text-align:left;">

```
$ git pull origin main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور دقیقاً معادل اجرای پیاپی این دو دستور است:

</div>

<div style="text-align:left;">

```
$ git fetch origin
$ git merge origin/main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نمودار زیر این تفاوت را به‌روشنی نشان می‌دهد:

</div>

<div style="text-align:left;">

</div>

توصیه‌ی عملی این است: اگر می‌خواهید کنترل بیشتری روی این‌که *چه زمانی* تغییرات دیگران با کد شما ترکیب شود داشته باشید، از ‪fetch‬ استفاده کنید و ادغام را دستی و آگاهانه انجام دهید. اگر فقط می‌خواهید سریع خودتان را به‌روز کنید و مطمئن هستید تعارضی پیش نمی‌آید، ‪pull‬ سریع‌تر است.

### استفاده از rebase به‌جای merge هنگام pull

همان‌طور که در فصل ۴ دیدیم، rebase تاریخچه‌ای خطی‌تر می‌سازد. اگر ترجیح می‌دهید ‪pull‬ به‌جای ادغام، از rebase استفاده کند (که تاریخچه‌ی محلی شما را تمیزتر نگه می‌دارد و از کامیت‌های ادغام بی‌مورد جلوگیری می‌کند)، از فلگ ‪--rebase‬ استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git pull --rebase origin main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

بسیاری از توسعه‌دهندگان حرفه‌ای، این رفتار را به‌طور دائمی و پیش‌فرض تنظیم می‌کنند:

</div>

<div style="text-align:left;">

```
$ git config --global pull.rebase true
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۵.۶ کار با شاخه‌های ریموت

وقتی یک مخزن را کلون می‌کنید یا ‪fetch‬ می‌زنید، Git شاخه‌های ریموت را با پیشوند نام ریموت نشان می‌دهد، مثل ‪origin/feature-x‬. برای دیدن فهرست همه‌ی شاخه‌ها، هم محلی و هم ریموت:

</div>

<div style="text-align:left;">

```
$ git branch --all
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر همکارتان شاخه‌ای به نام ‪serverfix‬ روی ریموت ساخته و شما می‌خواهید روی همان شاخه محلی کار کنید، می‌توانید یک شاخه‌ی محلی بسازید که آن را «ردیابی» (track) کند:

</div>

<div style="text-align:left;">

```
$ git checkout --track origin/serverfix
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، شاخه‌ی محلی ‪serverfix‬ را دقیقاً از همان نقطه‌ای که ‪origin/serverfix‬ هست می‌سازد، و آن را طوری تنظیم می‌کند که با ‪git pull‬ ساده (بدون نیاز به نوشتن نام ریموت و شاخه)، به‌طور خودکار با همان شاخه‌ی ریموت به‌روز شود؛ به این ارتباط، «شاخه‌ی upstream» گفته می‌شود.

اگر می‌خواهید یک شاخه‌ی محلی را برای اولین‌بار push کنید، اما با نام متفاوتی روی ریموت:

</div>

<div style="text-align:left;">

```
$ git push origin local-name:remote-name
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### حذف یک شاخه‌ی ریموت

برای حذف یک شاخه از روی سرور ریموت (نه فقط محلی خودتان):

</div>

<div style="text-align:left;">

```
$ git push origin --delete old-feature
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۵.۷ حذف یک ریموت

اگر دیگر نیازی به یک ریموت خاص ندارید (مثلاً اتصال به یک فورک قدیمی)، می‌توانید آن اتصال را حذف کنید:

</div>

<div style="text-align:left;">

```
$ git remote remove old-origin
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

توجه کنید: این کار فقط اتصال *محلی* شما به آن ریموت را پاک می‌کند؛ خود مخزن روی سرور (مثلاً روی GitHub) هیچ تغییری نمی‌کند و دست‌نخورده باقی می‌ماند.

### ۵.۸ حالا چه؟

در این فصل، یاد گرفتید چگونه یک مخزن را کلون کنید، یک مخزن محلی موجود را به یک ریموت متصل کنید، و مهم‌تر از همه، تفاوت اساسی بین ‪fetch‬ (فقط دانلود) و ‪pull‬ (دانلود و ادغام فوری) را با جزئیات کامل درک کردید. همچنین با شاخه‌های ریموت و مفهوم شاخه‌ی upstream آشنا شدید.

اما دنیای واقعی همیشه بی‌نقص پیش نمی‌رود. دیر یا زود، یک کامیت اشتباه ثبت می‌کنید، یک فایل را ناخواسته حذف می‌کنید، یا می‌خواهید کاری را که تازه انجام داده‌اید، کاملاً برگردانید. در فصل بعد، به سراغ ابزارهایی می‌رویم که Git برای دقیقاً همین موقعیت‌ها در اختیارتان می‌گذارد.

### برای مرجع بعدی

## فصل ۶

### <u>بازگرداندن تغییرات و مدیریت اشتباهات</u>

هر توسعه‌دهنده‌ای، صرف‌نظر از میزان تجربه‌اش، دیر یا زود اشتباه می‌کند: کامیتی با پیام اشتباه، فایلی که نباید تغییر می‌کرد، یا حتی یک ‪reset --hard‬ ناخواسته که به نظر می‌رسد کل روز کاری را از بین برده. خبر خوب این است که Git، به لطف همان معماری قدرتمندش، تقریباً همیشه یک راه بازگشت دارد. در این فصل، با مهم‌ترین ابزارهای بازگرداندن تغییرات آشنا می‌شوید: ‪restore‬، ‪reset‬، ‪revert‬، ‪stash‬، و مهم‌تر از همه، شبکه‌ی ایمنی نهایی Git، یعنی ‪reflog‬.

### ۶.۱ بازگرداندن فایل‌های درخت کاری با ‪git restore‬

فرض کنید فایلی را در درخت کاری تغییر داده‌اید، اما هنوز آن را مرحله‌بندی (‪git add‬) نکرده‌اید، و حالا پشیمان شده‌اید و می‌خواهید به نسخه‌ی آخرین کامیت برگردید:

</div>

<div style="text-align:left;">

```
$ git restore config.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، محتوای فایل را دقیقاً به همان چیزی که در آخرین کامیت بود برمی‌گرداند و تغییرات مرحله‌بندی‌نشده‌ی شما را دور می‌ریزد. اگر فایلی را از قبل مرحله‌بندی کرده باشید و بخواهید فقط آن را از ناحیه‌ی مرحله‌بندی بیرون بیاورید (بدون این‌که خود تغییرات را از درخت کاری پاک کنید)، از ‪--staged‬ استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git restore --staged config.txt
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

با این دستور، فایل به وضعیت «تغییریافته اما مرحله‌بندی‌نشده» برمی‌گردد؛ خود تغییرات هنوز روی دیسک هستند، فقط دیگر آماده‌ی کامیت شدن نیستند.

### ۶.۲ سه سطح ‪git reset‬: soft، mixed، و hard

دستور ‪git reset‬ اشاره‌گر شاخه‌ی فعلی شما را به یک کامیت دیگر (معمولاً یکی از کامیت‌های قبلی) منتقل می‌کند. اما نکته‌ی مهم این است که ‪reset‬ سه «سطح» متفاوت دارد که هرکدام، علاوه بر جابه‌جا کردن اشاره‌گر، رفتار متفاوتی با ناحیه‌ی مرحله‌بندی و درخت کاری شما دارند. به یاد بیاورید که در فصل ۱، سه ناحیه‌ی Git، یعنی درخت کاری، ناحیه‌ی مرحله‌بندی، و مخزن را دیدیم؛ حالا وقت آن رسیده که ببینیم reset دقیقاً روی هرکدام چه اثری می‌گذارد.

### ‪--soft‬: فقط اشاره‌گر کامیت را جابه‌جا کن

</div>

<div style="text-align:left;">

```
$ git reset --soft HEAD~1
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، آخرین کامیت را «باز می‌کند»، اما تمام تغییراتش را در ناحیه‌ی مرحله‌بندی نگه می‌دارد؛ انگار همان کامیت را هرگز نساخته بودید، اما ‪git add‬ آن را زده بودید. این حالت به‌خصوص برای ترکیب چند کامیت آخر در یک کامیت واحد، بدون رفتن به سراغ rebase تعاملی، بسیار کاربردی است.

### ‪--mixed‬: اشاره‌گر را جابه‌جا کن و از مرحله‌بندی خارج کن (پیش‌فرض)

</div>

<div style="text-align:left;">

```
$ git reset HEAD~1
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر هیچ فلگی ننویسید، Git از حالت ‪--mixed‬ استفاده می‌کند. این حالت، مثل ‪--soft‬، کامیت را باز می‌کند، اما تغییرات را از ناحیه‌ی مرحله‌بندی هم خارج می‌کند؛ آن‌ها همچنان در درخت کاری شما، به‌صورت تغییرات مرحله‌بندی‌نشده، باقی می‌مانند. این حالت زمانی مفید است که کامیتی زودهنگام ساخته‌اید و می‌خواهید دوباره، این‌بار با دقت بیشتر، تصمیم بگیرید چه چیزی مرحله‌بندی شود.

### ‪--hard‬: همه‌چیز را با نسخه‌ی هدف یکسان کن

</div>

<div style="text-align:left;">

```
$ git reset --hard HEAD~1
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این خطرناک‌ترین حالت ‪reset‬ است: اشاره‌گر کامیت را جابه‌جا می‌کند، ناحیه‌ی مرحله‌بندی را پاک می‌کند، *و درخت کاری را هم دقیقاً با نسخه‌ی هدف یکسان می‌کند*. هر تغییری که مرحله‌بندی‌نشده و کامیت‌نشده باشد، برای همیشه از بین می‌رود، بدون هیچ اخطار یا تأییدیه‌ای. یک عادت امنیتی بسیار خوب، همیشه پیش از اجرای ‪reset --hard‬، اجرای ‪git status‬ و ‪git diff‬ برای اطمینان کامل از این‌که واقعاً می‌خواهید این تغییرات دور ریخته شوند.

### ۶.۳ قانون مهم: reset برای محلی، revert برای عمومی

دقیقاً مثل rebase در فصل ۴، ‪reset‬ هم *تاریخچه را بازنویسی* می‌کند (اشاره‌گر شاخه را به عقب می‌برد). این یعنی همان قانون طلایی این‌جا هم صدق می‌کند: هرگز ‪reset‬ را روی کامیت‌هایی که قبلاً push کرده‌اید و دیگران احتمالاً آن‌ها را گرفته‌اند، اجرا نکنید.

برای موقعیتی که می‌خواهید اثر یک کامیت *عمومی و مشترک* را خنثی کنید، Git ابزار امن‌تری دارد: ‪git revert‬. به‌جای پاک کردن یا جابه‌جا کردن کامیت قبلی، ‪revert‬ یک کامیت *تازه* می‌سازد که دقیقاً اثر معکوس آن کامیت قدیمی را اعمال می‌کند:

</div>

<div style="text-align:left;">

```
$ git revert a1b2c3d
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

Git ویرایشگر متن را باز می‌کند تا پیام این کامیت تازه را (که به‌طور پیش‌فرض چیزی مثل «Revert "Add payment endpoint"» است) تأیید کنید. تفاوت کلیدی این است: تاریخچه‌ی قدیمی *دست‌نخورده* باقی می‌ماند؛ فقط یک کامیت تازه به آن اضافه می‌شود که اثر کامیت قبلی را خنثی می‌کند. این یعنی همکارانتان، وقتی این کامیت را ‪pull‬ می‌کنند، هیچ تعارض یا سردرگمی‌ای در تاریخچه نمی‌بینند؛ برایشان کاملاً شبیه هر کامیت معمولی دیگری است.

قاعده‌ی ساده و کاربردی: ‪reset‬ برای پاکسازی‌های محلی و شخصی؛ ‪revert‬ برای اصلاحات مشترک و اشتراک‌گذاری‌شده.

### ۶.۴ کنار گذاشتن موقت تغییرات با ‪git stash‬

گاهی وسط کار روی یک ویژگی، ناگهان لازم می‌شود سریع به شاخه‌ی دیگری بروید (مثلاً برای رفع یک اشکال فوری)، اما تغییرات فعلی‌تان هنوز آماده‌ی کامیت نیستند. ‪git stash‬ دقیقاً برای همین موقعیت طراحی شده: تمام تغییرات درخت کاری و ناحیه‌ی مرحله‌بندی را، به‌طور موقت، در یک «انبار» جداگانه ذخیره می‌کند و درخت کاری شما را تمیز و مثل آخرین کامیت برمی‌گرداند:

</div>

<div style="text-align:left;">

```
$ git stash
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

حالا می‌توانید آزادانه به شاخه‌ی دیگر بروید، کار فوری خود را انجام دهید، و برگردید. برای بازگرداندن تغییرات ذخیره‌شده:

</div>

<div style="text-align:left;">

```
$ git stash pop
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

‪pop‬ هم تغییرات را برمی‌گرداند و هم آن‌ها را از فهرست انبار حذف می‌کند. اگر می‌خواهید تغییرات را برگردانید اما نسخه‌اش را هم در انبار نگه دارید (برای اطمینان بیشتر)، از ‪apply‬ به‌جای ‪pop‬ استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git stash apply
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

می‌توانید چندین بار ‪stash‬ بزنید؛ Git آن‌ها را به‌صورت یک پشته (stack) نگه می‌دارد. برای دیدن فهرست همه‌ی موارد ذخیره‌شده:

</div>

<div style="text-align:left;">

```
$ git stash list
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برای ذخیره با یک پیام توصیفی (که پیدا کردن یک stash خاص در آینده را راحت‌تر می‌کند):

</div>

<div style="text-align:left;">

```
$ git stash push -m "WIP: refactoring payment logic"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۶.۵ شبکه‌ی ایمنی نهایی: ‪git reflog‬

حالا به یکی از مهم‌ترین ابزارهایی می‌رسیم که هر کاربر Git، دیر یا زود، به آن نیاز پیدا می‌کند. فرض کنید یک ‪reset --hard‬ اشتباه زدید و کامیت‌های مهمی را از دست دادید، یا در حین یک rebase پیچیده، چیزی به‌کلی خراب شد. آیا آن کار واقعاً برای همیشه از بین رفته؟ در اکثر موارد، نه.

Git، در پس‌زمینه، یک ثبت (log) کاملاً جداگانه از *هر حرکتی* که اشاره‌گر ‪HEAD‬ در طول زمان انجام داده نگه می‌دارد؛ به این ثبت، ‪reflog‬ گفته می‌شود. حتی اگر یک کامیت دیگر از هیچ شاخه‌ای قابل‌دسترسی نباشد، تا زمانی که در reflog ثبت شده باشد (که معمولاً حدود ۹۰ روز برای reflog خود HEAD نگه‌داری می‌شود)، هنوز می‌توانید آن را پیدا کنید:

</div>

<div style="text-align:left;">

```
$ git reflog
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
b3f9d17 HEAD@{0}: reset: moving to HEAD~1
a1b2c3d HEAD@{1}: commit: Add payment endpoint
7890abc HEAD@{2}: commit: Fix typo in payment model
d4e5f6a HEAD@{3}: commit: Initial payment work
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

هر خط، یک نقطه در زمان است که ‪HEAD‬ به آن اشاره می‌کرده، همراه با نوع عملیاتی که باعث آن حرکت شده (کامیت، reset، checkout، rebase، و غیره). اگر ببینید کامیت گم‌شده‌ی شما (در این مثال، ‪a1b2c3d‬) هنوز در این فهرست هست، می‌توانید به‌سادگی به آن نقطه بازگردید:

</div>

<div style="text-align:left;">

```
$ git reset --hard a1b2c3d
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا اگر ترجیح می‌دهید فقط آن کامیت خاص را، بدون تغییر بقیه‌ی وضعیت فعلی، بازیابی کنید، می‌توانید از ‪cherry-pick‬ (که در فصل ۴ دیدیم) هم استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git cherry-pick a1b2c3d
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یک محدودیت مهم را باید بدانید: ‪reflog‬ فقط *کامیت‌ها* را می‌تواند نجات دهد، نه تغییراتی که هرگز کامیت نشده بودند. اگر فایلی را تغییر داده‌اید اما هرگز ‪git add‬ و ‪git commit‬ نکرده‌اید، و بعد ‪reset --hard‬ زدید، آن تغییرات، متأسفانه، واقعاً و برای همیشه از بین رفته‌اند؛ هیچ reflog ای نمی‌تواند چیزی را که هرگز به‌عنوان یک عکس فوری ثبت نشده، بازیابی کند. دقیقاً به همین دلیل است که عادت کامیت کردن مکرر (حتی کامیت‌های ناقص که بعداً با rebase تعاملی تمیزشان می‌کنید)، یک عادت امنیتی بسیار ارزشمند است.

### ۶.۶ جدول خلاصه: کدام ابزار برای کدام موقعیت

| موقعیت | ابزار مناسب |
|---|---|
| برگرداندن یک فایل تغییریافته و کامیت‌نشده | git restore FILE |
| خارج کردن یک فایل از مرحله‌بندی، بدون از دست دادن تغییرات | git restore --staged FILE |
| باز کردن کامیت اخیر، نگه‌داشتن تغییرات به‌صورت مرحله‌بندی‌شده | git reset --soft HEAD~1 |
| باز کردن کامیت اخیر، نگه‌داشتن تغییرات به‌صورت مرحله‌بندی‌نشده | git reset HEAD~1 |
| دور ریختن کامل یک کامیت و همه‌ی تغییرات مرتبط با آن (محلی) | git reset --hard HEAD~1 |
| خنثی کردن یک کامیت که قبلاً push شده و عمومی است | git revert HASH |
| ذخیره‌ی موقت کار ناتمام برای رفتن سراغ کار دیگر | git stash |
| بازیابی کاری که به‌نظر برای همیشه از دست رفته | git reflog |

### ۶.۷ حالا چه؟

در این فصل، با مهم‌ترین ابزارهای بازگرداندن تغییرات در Git آشنا شدید: ‪restore‬ برای فایل‌های تکی، سه سطح ‪reset‬ برای جابه‌جا کردن اشاره‌گر کامیت با اثرات متفاوت، ‪revert‬ برای اصلاحات امن در تاریخچه‌ی عمومی، ‪stash‬ برای کنار گذاشتن موقت کار، و مهم‌تر از همه، ‪reflog‬ به‌عنوان شبکه‌ی ایمنی نهایی که در اکثر موقعیت‌های اضطراری می‌تواند کار «گم‌شده»ی شما را نجات دهد.

تا این‌جا یاد گرفتیم چگونه اشتباهات را برطرف کنیم. در فصل بعد، مهارت مکملی یاد می‌گیریم: چگونه در تاریخچه‌ی یک پروژه به‌طور عمیق جست‌وجو کنیم تا اصلاً بفهمیم مشکل از کجا شروع شده، چه کسی چه خطی را نوشته، و حتی با جست‌وجوی دودویی، دقیقاً کدام کامیت یک باگ را وارد کد کرده است.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| git restore FILE | فایل مرحله‌بندی‌نشده را به وضعیت آخرین کامیت برمی‌گرداند. |
| git restore --staged FILE | فایل را از ناحیه‌ی مرحله‌بندی خارج می‌کند، تغییرات را در درخت کاری نگه می‌دارد. |
| git reset --soft COMMIT | اشاره‌گر را جابه‌جا می‌کند، تغییرات را مرحله‌بندی‌شده نگه می‌دارد. |
| git reset COMMIT | اشاره‌گر را جابه‌جا می‌کند و تغییرات را از مرحله‌بندی خارج می‌کند (پیش‌فرض). |
| git reset --hard COMMIT | اشاره‌گر را جابه‌جا کرده و درخت کاری را کاملاً بازنویسی می‌کند (تغییرات از بین می‌روند). |
| git revert HASH | یک کامیت تازه می‌سازد که اثر کامیت مشخص‌شده را خنثی می‌کند؛ امن برای تاریخچه‌ی عمومی. |
| git stash | تغییرات فعلی را موقتاً کنار می‌گذارد و درخت کاری را تمیز می‌کند. |
| git stash push -m "MSG" | مثل بالا، اما با یک پیام توصیفی برای شناسایی بعدی. |
| git stash list | فهرست همه‌ی موارد ذخیره‌شده در انبار را نمایش می‌دهد. |
| git stash pop | آخرین مورد انبارشده را بازمی‌گرداند و از فهرست انبار حذف می‌کند. |
| git stash apply | آخرین مورد انبارشده را بازمی‌گرداند، اما در انبار هم نگه می‌دارد. |
| git reflog | ثبت کامل حرکت‌های HEAD در طول زمان را نمایش می‌دهد؛ برای بازیابی کار گم‌شده. |

</div>

## فصل ۷

### <u>کاوش عمیق در تاریخچه</u>

در فصل قبل، ابزارهای بازگرداندن تغییرات را دیدیم. اما گاهی، پیش از این‌که بتوانید چیزی را برگردانید، باید بفهمید اصلاً *چه اتفاقی افتاده*: چه کسی این خط را نوشته؟ این باگ از کِی وارد کد شده؟ کدام کامیت، دقیقاً، این تغییر رفتار عجیب را ایجاد کرده؟ در این فصل، با ابزارهایی آشنا می‌شوید که تاریخچه‌ی یک پروژه‌ی Git را از یک بایگانی ساده، به یک ابزار قدرتمند برای اشکال‌زدایی و کاوش تبدیل می‌کنند.

### ۷.۱ فیلتر کردن و جست‌وجوی پیشرفته در ‪git log‬

در فصل ۲، با شکل‌های ساده‌ی ‪git log‬ آشنا شدیم. حالا وقت آن است که ببینیم این دستور، با گزینه‌های درست، به چه ابزار قدرتمندی برای جست‌وجو در تاریخچه تبدیل می‌شود.

### فیلتر بر اساس زمان

</div>

<div style="text-align:left;">

```
$ git log --since="2 weeks ago"
$ git log --until="2026-01-01"
$ git log --since="2026-01-01" --until="2026-01-31"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### فیلتر بر اساس نویسنده

</div>

<div style="text-align:left;">

```
$ git log --author="Ali"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### جست‌وجو در پیام‌های کامیت

</div>

<div style="text-align:left;">

```
$ git log --grep="security fix"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### جست‌وجوی محتوایی با Pickaxe: کدام کامیت این خط را اضافه یا حذف کرد

یکی از قدرتمندترین و کمتر شناخته‌شده‌ترین قابلیت‌های ‪log‬، گزینه‌ی ‪-S‬ (که به آن «pickaxe» هم گفته می‌شود) است. این گزینه، برخلاف ‪--grep‬ که در *پیام* کامیت جست‌وجو می‌کند، در *محتوای واقعی تغییرات* جست‌وجو می‌کند و کامیت‌هایی را پیدا می‌کند که تعداد دفعات ظهور یک رشته‌ی مشخص را در فایل تغییر داده‌اند (یعنی آن را اضافه یا حذف کرده‌اند):

</div>

<div style="text-align:left;">

```
$ git log -S "calculateDiscount"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور دقیقاً همان کامیت‌هایی را پیدا می‌کند که تابع ‪calculateDiscount‬ در آن‌ها اضافه یا حذف شده؛ ابزاری فوق‌العاده وقتی می‌خواهید بدانید یک قطعه‌ی کد مشخص از کجا آمده. برای جست‌وجوی مبتنی بر عبارت باقاعده به‌جای یک رشته‌ی ثابت، از ‪-G‬ استفاده کنید.

### محدود کردن به یک فایل خاص

</div>

<div style="text-align:left;">

```
$ git log -- path/to/file.js
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

و اگر می‌خواهید حتی از میان تغییر نام‌های آن فایل هم عبور کند (یعنی تاریخچه‌اش را حتی از پیش از این‌که نامش عوض شود دنبال کند):

</div>

<div style="text-align:left;">

```
$ git log --follow -- path/to/file.js
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### نمایش گرافیکی شاخه‌ها با ‪--graph‬

برای دیدن یک نمای تصویری (با کاراکترهای ASCII) از این‌که چگونه شاخه‌ها منشعب و دوباره ادغام شده‌اند:

</div>

<div style="text-align:left;">

```
$ git log --graph --oneline --all --decorate
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
*   0e25143 (HEAD, main) Merge branch 'feature'
|\
| * 16b36c6 Fix a bug in the new feature
| * 23ad9ad Start a new feature
* | ad8621a Fix a critical security issue
|/
* 400e4b7 Fix typos in the documentation
* 160e224 Add the initial code base
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این ترکیب از فلگ‌ها، که یکی از پرکاربردترین ترکیب‌های ‪log‬ در میان توسعه‌دهندگان حرفه‌ای است، ‪--decorate‬ (نمایش نام شاخه‌ها و تگ‌ها کنار هر کامیت)، ‪--all‬ (نمایش همه‌ی شاخه‌ها، نه فقط شاخه‌ی فعلی)، و ‪--graph‬ (رسم خطوط اتصال) را با هم ترکیب می‌کند تا یک نمای کامل از ساختار تاریخچه ارائه دهد.

### خلاصه‌ی مشارکت هر توسعه‌دهنده

برای دیدن این‌که هرکدام از اعضای تیم چند کامیت داشته‌اند:

</div>

<div style="text-align:left;">

```
$ git shortlog -n
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

فلگ ‪-n‬ خروجی را بر اساس تعداد کامیت هر فرد، به‌جای ترتیب حروف الفبا، مرتب می‌کند.

### ۷.۲ فهمیدن این‌که چه کسی هر خط را نوشته: ‪git blame‬

فرض کنید به خطی عجیب از کد رسیده‌اید و می‌خواهید بدانید چرا نوشته شده، چه کسی آن را نوشته، و در چه کامیتی. دستور ‪git blame‬ دقیقاً برای همین طراحی شده: هر خط از یک فایل را با شناسه‌ی کامیت، نویسنده، و تاریخی که *آخرین‌بار* آن خط تغییر کرده، حاشیه‌نویسی می‌کند:

</div>

<div style="text-align:left;">

```
$ git blame app/models/user.rb
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
a1b2c3d4 (John Doe  2026-03-15 14:00:00) 10: const API_URL = "http://localhost:8080";
f5e6d7c8 (Jane Smith 2026-04-01 09:30:00) 11: console.log("Starting app...");
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

می‌توانید این خروجی را برای یک بازه‌ی مشخص از خطوط محدود کنید (برای فایل‌های بزرگ، که دیدن حاشیه‌نویسی کل فایل عملی نیست):

</div>

<div style="text-align:left;">

```
$ git blame -L 66,71 app/models/user.rb
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برای دیدن ایمیل کامل نویسنده به‌جای فقط نامش:

</div>

<div style="text-align:left;">

```
$ git blame -e app/models/user.rb
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### رد شدن از تغییر نام فایل با ‪--follow‬

اگر فایل مورد نظر شما، در طول تاریخچه‌اش، تغییر نام هم داده باشد، فلگ ‪--follow‬ کمک می‌کند blame از میان آن تغییر نام هم عبور کند و تاریخچه‌ی کامل هر خط را دنبال کند.

### قانون طلایی: blame برای وقتی می‌دانید کجا نگاه کنید

نکته‌ی مهمی که باید در نظر داشته باشید: ‪git blame‬ زمانی مفید است که *می‌دانید* کدام فایل و کدام خط مشکل‌ساز است، و فقط می‌خواهید بدانید چرا و توسط چه کسی نوشته شده. اما اگر اصلاً نمی‌دانید مشکل کجاست، و فقط می‌دانید «این ویژگی قبلاً کار می‌کرد، الان نمی‌کند»، ابزار مناسب چیز دیگری است که در بخش بعد می‌بینیم.

### ۷.۳ جست‌وجوی دودویی برای پیدا کردن باگ: ‪git bisect‬

فرض کنید مطمئن هستید نسخه‌ی یک ماه پیش پروژه‌تان (که با تگ ‪v2.0‬ مشخص شده) درست کار می‌کرد، اما نسخه‌ی فعلی یک باگ عجیب دارد. بین این دو نقطه، ممکن است صدها کامیت وجود داشته باشد؛ بررسی دستی یکی‌یکی آن‌ها می‌تواند ساعت‌ها طول بکشد. ‪git bisect‬ دقیقاً همین مشکل را با یک الگوریتم جست‌وجوی دودویی (binary search) حل می‌کند: به‌جای بررسی خطی، هر بار دقیقاً وسط بازه‌ی مشکوک را بررسی می‌کند، و با هر پاسخ شما (خوب یا بد)، نیمی از فضای جست‌وجو را کنار می‌گذارد.

برای شروع یک نشست bisect:

</div>

<div style="text-align:left;">

```
$ git bisect start
$ git bisect bad
$ git bisect good v2.0
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خط اول نشست را شروع می‌کند، خط دوم می‌گوید کامیت *فعلی* (که در آن هستید) دارای باگ است، و خط سوم می‌گوید تگ ‪v2.0‬ سالم بوده است. Git بلافاصله شما را به کامیتی دقیقاً در وسط این بازه منتقل می‌کند:

</div>

<div style="text-align:left;">

```
Bisecting: 675 revisions left to test after this (roughly 10 steps)
[f23d45e] Fix login validation logic
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

حالا نوبت شماست: کد را کامپایل یا اجرا کنید، تست کنید ببینید باگ هست یا نه، و بر اساس نتیجه، یکی از این دو دستور را بزنید:

</div>

<div style="text-align:left;">

```
$ git bisect good
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

یا

</div>

<div style="text-align:left;">

```
$ git bisect bad
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

Git، بر اساس پاسخ شما، نیمی از فضای باقی‌مانده را کنار می‌گذارد و دوباره شما را به کامیت میانیِ بازه‌ی جدید منتقل می‌کند. این چرخه را تکرار می‌کنید تا وقتی که Git اعلام کند دیگر کامیت بیشتری برای بررسی نمانده و دقیقاً کامیتی که باگ را وارد کرده مشخص شود:

</div>

<div style="text-align:left;">

```
a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0 is the first bad commit
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

از آن‌جا که این جست‌وجو دودویی است، حتی برای هزار کامیت، فقط حدود ده مرحله (لگاریتم پایه‌ی ۲ هزار) لازم است تا کامیت مقصر پیدا شود؛ سرعتی که با بررسی خطی هرگز قابل‌مقایسه نیست.

پس از پیدا کردن مقصر، برای بازگشت به وضعیت عادی (بازگشت به همان شاخه‌ای که پیش از شروع bisect روی آن بودید):

</div>

<div style="text-align:left;">

```
$ git bisect reset
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### خودکارسازی کامل با ‪git bisect run‬

اگر یک اسکریپت یا مجموعه تست خودکار دارید که می‌تواند به‌طور برنامه‌ای تشخیص دهد باگ وجود دارد یا نه (و کد بازگشتی صفر برای «خوب» و غیرصفر برای «بد» برمی‌گرداند)، می‌توانید کل فرایند bisect را کاملاً خودکار کنید، بدون این‌که حتی یک‌بار هم دستی تست کنید:

</div>

<div style="text-align:left;">

```
$ git bisect start
$ git bisect bad HEAD
$ git bisect good v2.0
$ git bisect run npm test
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

Git خودش، برای هر کامیت میانی، آن اسکریپت را اجرا می‌کند، نتیجه را تفسیر می‌کند، و بدون هیچ دخالت انسانی، مستقیماً به کامیت مقصر می‌رسد.

### ۷.۴ نشانه‌گذاری نقاط مهم با ‪git tag‬

در طول این فصل، چند بار به تگ‌هایی مثل ‪v2.0‬ اشاره کردیم. تگ‌ها، نشانه‌های ثابت و دائمی روی یک کامیت مشخص هستند، که معمولاً برای علامت‌گذاری نسخه‌های رسمی یک نرم‌افزار (مثل ‪v1.0.0‬) استفاده می‌شوند. برخلاف شاخه‌ها که اشاره‌گرشان با هر کامیت تازه جلو می‌رود، یک تگ همیشه به همان یک کامیت خاص اشاره می‌کند و هرگز حرکت نمی‌کند.

### دو نوع تگ

تگ سبک‌وزن (lightweight) فقط یک اشاره‌گر ساده به یک کامیت است، بدون هیچ اطلاعات اضافه‌ای:

</div>

<div style="text-align:left;">

```
$ git tag v1.0.0
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

تگ حاشیه‌دار (annotated)، که برای انتشارهای رسمی توصیه می‌شود، اطلاعات اضافه‌ای مثل نام تگ‌گذار، تاریخ، و یک پیام کامل، شبیه به یک کامیت واقعی، در خودش ذخیره می‌کند:

</div>

<div style="text-align:left;">

```
$ git tag -a v1.0.0 -m "First stable release"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر بخواهید یک کامیت *قدیمی‌تر* (نه آخرین کامیت فعلی) را تگ بزنید، شناسه‌اش را هم اضافه کنید:

</div>

<div style="text-align:left;">

```
$ git tag -a v1.0.0 a1b2c3d4 -m "First stable release"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### فهرست کردن و حذف تگ‌ها

</div>

<div style="text-align:left;">

```
$ git tag
$ git tag -d v1.0.0
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ارسال تگ‌ها به ریموت

نکته‌ی مهم: برخلاف کامیت‌ها، تگ‌ها به‌طور خودکار با ‪git push‬ ساده فرستاده *نمی‌شوند*. باید صراحتاً درخواست کنید:

</div>

<div style="text-align:left;">

```
$ git push origin --tags
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

و برای حذف یک تگ از روی ریموت:

</div>

<div style="text-align:left;">

```
$ git push origin --delete v1.0.0
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۷.۵ حالا چه؟

در این فصل، از یک ابزار ساده‌ی نمایش تاریخچه (‪log‬ در فصل ۲) به یک جعبه‌ابزار کامل کاوش رسیدیم: فیلتر کردن بر اساس زمان، نویسنده، و پیام، جست‌وجوی محتوایی با pickaxe، نمایش گرافیکی شاخه‌ها، فهمیدن نویسنده‌ی هر خط با ‪blame‬، و مهم‌تر از همه، جست‌وجوی دودویی خودکار با ‪bisect‬ برای پیدا کردن دقیق کامیتی که یک باگ را وارد کرده. همچنین یاد گرفتید چگونه نقاط مهم تاریخچه را با تگ نشانه‌گذاری کنید.

تا این‌جا، بیشتر کارمان به‌عنوان یک فرد یا حداکثر با ابزارهای پایه‌ای همکاری بوده است. در فصل بعد، وارد دنیای واقعی همکاری تیمی حرفه‌ای می‌شویم: Fork کردن، Pull Request، بررسی کد، و مدل‌های گردش‌کاری که تیم‌های نرم‌افزاری واقعی هر روز از آن‌ها استفاده می‌کنند.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| git log --since / --until | کامیت‌ها را بر اساس بازه‌ی زمانی فیلتر می‌کند. |
| git log --author="NAME" | کامیت‌های یک نویسنده‌ی خاص را نمایش می‌دهد. |
| git log --grep="TEXT" | پیام‌های کامیت را به‌دنبال یک عبارت جست‌وجو می‌کند. |
| git log -S "STRING" | کامیت‌هایی که تعداد دفعات ظهور یک رشته را تغییر داده‌اند پیدا می‌کند (pickaxe). |
| git log --follow -- FILE | تاریخچه‌ی یک فایل را حتی از میان تغییر نام آن دنبال می‌کند. |
| git log --graph --oneline --all --decorate | نمای گرافیکی کامل از ساختار شاخه‌ها و ادغام‌ها نمایش می‌دهد. |
| git shortlog -n | خلاصه‌ی تعداد کامیت هر مشارکت‌کننده را نمایش می‌دهد. |
| git blame FILE | هر خط از فایل را با کامیت، نویسنده، و تاریخ آخرین تغییرش حاشیه‌نویسی می‌کند. |
| git blame -L START,END FILE | حاشیه‌نویسی را به یک بازه‌ی مشخص از خطوط محدود می‌کند. |
| git bisect start / good / bad | یک نشست جست‌وجوی دودویی برای پیدا کردن کامیت مقصر یک باگ آغاز می‌کند. |
| git bisect run SCRIPT | فرایند bisect را با یک اسکریپت تست خودکار، بدون دخالت دستی، انجام می‌دهد. |
| git bisect reset | نشست bisect را پایان داده و به شاخه‌ی اصلی بازمی‌گردد. |
| git tag NAME | یک تگ سبک‌وزن روی آخرین کامیت می‌سازد. |
| git tag -a NAME -m "MSG" | یک تگ حاشیه‌دار، همراه با پیام و اطلاعات کامل، می‌سازد. |
| git push origin --tags | همه‌ی تگ‌های محلی را به ریموت ارسال می‌کند. |

</div>

<div dir="rtl" lang="fa" style="text-align: right;">

## فصل ۸

### <u>همکاری تیمی و گردش‌کار حرفه‌ای</u>

در فصل‌های قبل، مهارت‌های فنی Git را به‌طور کامل پوشش دادیم. اما در دنیای واقعی، Git به‌ندرت به‌تنهایی و توسط یک نفر استفاده می‌شود؛ معمولاً تیم‌هایی از چند تا چند صد توسعه‌دهنده، روی یک مخزن مشترک همکاری می‌کنند. در این فصل، به سراغ فرایندها و ابزارهایی می‌رویم که این همکاری بزرگ‌مقیاس را ممکن می‌سازند: Fork کردن، Pull Request، بررسی کد، و مدل‌های گردش‌کار رایجی که تیم‌های نرم‌افزاری هر روز از آن‌ها استفاده می‌کنند.

### ۸.۱ Fork کردن: مالکیت کامل روی نسخه‌ی شخصی خودتان

وقتی می‌خواهید در یک پروژه‌ی متن‌باز که مالکش نیستید مشارکت کنید (یا حتی در بسیاری از شرکت‌ها که سیاست دسترسی محدودتری دارند)، معمولاً به‌طور مستقیم اجازه‌ی push کردن روی مخزن اصلی را ندارید. راه‌حل، Fork کردن است: در سرویس‌هایی مثل GitHub یا GitLab، یک دکمه‌ی «Fork» وجود دارد که یک کپی کامل از آن مخزن را، در حساب کاربری *شما*، می‌سازد. این کپی، از نظر Git، کاملاً مستقل است؛ شما مالک کامل آن هستید و می‌توانید هر کاری، از جمله push مستقیم، روی آن انجام دهید.

بعد از Fork کردن (که از طریق رابط وب سرویس انجام می‌شود، نه با دستور Git)، مخزن جدید را کلون می‌کنید:

</div>

<div style="text-align:left;">

```
$ git clone https://github.com/YOUR-USERNAME/example-project.git
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### اضافه کردن مخزن اصلی به‌عنوان upstream

برای این‌که بتوانید بعداً تغییرات تازه‌ی مخزن *اصلی* (که به آن upstream گفته می‌شود) را دریافت کنید، یک ریموت دوم اضافه می‌کنید:

</div>

<div style="text-align:left;">

```
$ git remote add upstream https://github.com/ORIGINAL-OWNER/example-project.git
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

از این پس، ریموت ‪origin‬ شما به فورک شخصی‌تان اشاره می‌کند (که به آن push می‌کنید)، و ریموت ‪upstream‬ به مخزن اصلی اشاره می‌کند (که فقط از آن ‪fetch‬ می‌کنید تا به‌روز بمانید):

</div>

<div style="text-align:left;">

```
$ git fetch upstream
$ git merge upstream/main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

</div>

</div>

</div>

<div style="text-align:left;">

```
$ git add .
$ git commit -m "Add search feature to product page"
$ git push origin feature/add-search
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

سپس به صفحه‌ی فورک خودتان روی GitHub می‌روید؛ معمولاً بلافاصله دکمه‌ای به شما پیشنهاد می‌دهد «Compare & pull request». روی آن کلیک می‌کنید، توضیحی از تغییراتتان می‌نویسید، و درخواست خود را به مخزن اصلی ارسال می‌کنید. از این لحظه، نگهدارندگان (maintainers) آن پروژه، تغییرات شما را بررسی می‌کنند، شاید نظراتی بدهند یا درخواست اصلاحاتی کنند، و در نهایت، اگر تأیید شود، آن را در مخزن اصلی ادغام می‌کنند.

### ۸.۳ بررسی کد (Code Review)

Pull Request در عمل، بیشتر از یک ابزار فنی، یک ابزار *گفت‌وگو* است. هر خط تغییریافته، در رابط وب، قابل‌کامنت‌گذاری است؛ همکاران می‌توانند سؤال بپرسند، پیشنهاد بدهند، یا مشکلی را نشان دهند، پیش از این‌که کد وارد پروژه‌ی اصلی شود. چند عادت خوب که در اکثر تیم‌های حرفه‌ای رعایت می‌شود:

- کامیت‌های کوچک و معنادار بسازید؛ هر کامیت باید یک تغییر منطقی و قابل‌فهم را نشان دهد (به یاد بیاورید که در فصل ۴، با rebase تعاملی، یاد گرفتیم چگونه پیش از باز کردن Pull Request، این کامیت‌ها را تمیز کنیم).
- پیام کامیت‌های معنادار بنویسید (طبق چیزی که در فصل ۲ درباره‌ی خط اول کوتاه و توضیح مفصل‌تر گفتیم).
- پیش از push کردن، همیشه آخرین تغییرات شاخه‌ی اصلی را در شاخه‌ی خودتان بیاورید (با ‪pull‬ یا ‪rebase‬) تا از تعارض‌های بزرگ در لحظه‌ی آخر جلوگیری شود.
- به بازخورد بررسی‌کننده‌ها با روحیه‌ی باز پاسخ دهید؛ کامیت‌های تازه به همان شاخه اضافه کنید تا نظرات را برطرف کنید، و Pull Request به‌طور خودکار به‌روز می‌شود.

### ۸.۴ مدل‌های گردش‌کار رایج

تیم‌های مختلف، بسته به اندازه، سرعت انتشار، و پیچیدگی پروژه‌شان، از الگوهای متفاوتی برای سازماندهی شاخه‌ها استفاده می‌کنند. بیایید سه مدل رایج را با هم مقایسه کنیم.

### GitHub Flow: ساده و سریع

GitHub Flow، ساده‌ترین و سبک‌ترین مدل است: فقط یک شاخه‌ی همیشگی به نام ‪main‬ وجود دارد که همیشه باید آماده‌ی انتشار (production-ready) باشد، و هر ویژگی یا رفع اشکال، در یک شاخه‌ی کوتاه‌عمر جداگانه ساخته می‌شود:

</div>

<div style="text-align:left;">

```
$ git checkout main
$ git pull
$ git checkout -b feature/user-authentication
$ git add .
$ git commit -m "feat: add JWT token validation"
$ git push -u origin feature/user-authentication
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

سپس یک Pull Request باز می‌کنید، پس از بررسی و تأیید، مستقیماً در ‪main‬ ادغام می‌شود و معمولاً بلافاصله منتشر (deploy) می‌شود. این مدل برای تیم‌هایی که به‌طور مداوم و مکرر منتشر می‌کنند (continuous deployment) بسیار مناسب است.

### Git Flow: ساختاریافته برای انتشارهای زمان‌بندی‌شده

Git Flow، که پیچیده‌تر است، برای پروژه‌های بزرگ‌تر با برنامه‌ی انتشار مشخص و نسخه‌های رسمی طراحی شده. این مدل چند شاخه‌ی دائمی دارد:

- ‪main‬: همیشه نشان‌دهنده‌ی وضعیت *منتشرشده* و پایدار کد است.
- ‪develop‬: آخرین تغییرات توسعه، که هنوز آماده‌ی انتشار نیستند.
- ‪feature/*‬: شاخه‌های کوتاه‌عمر برای هر ویژگی، که از ‪develop‬ منشعب و دوباره به آن ادغام می‌شوند.
- ‪release/*‬: وقتی ‪develop‬ برای یک انتشار آماده می‌شود، یک شاخه‌ی release ساخته می‌شود تا آخرین پرداخت‌ها و رفع اشکالات جزئی پیش از انتشار در آن انجام شود.
- ‪hotfix/*‬: برای رفع فوری مشکلات حیاتی در نسخه‌ی *منتشرشده*، مستقیماً از ‪main‬ منشعب و به هر دوی ‪main‬ و ‪develop‬ ادغام می‌شود.

این ساختار، مناسب پروژه‌هایی است که چرخه‌ی انتشار رسمی و منظمی دارند (مثل نرم‌افزارهای دسکتاپ یا موبایل با نسخه‌های شماره‌گذاری‌شده)، اما برای تیم‌های کوچک یا پروژه‌هایی با انتشار مداوم، اغلب پیچیدگی غیرضروری اضافه می‌کند.

### گردش‌کار Fork-محور (Forking Workflow)

همان‌طور که در بخش ۸.۱ و ۸.۲ دیدیم، این مدل برای پروژه‌های متن‌باز، جایی که مشارکت‌کنندگان دسترسی مستقیم به مخزن اصلی ندارند، ایده‌آل است. تفاوت اصلی این مدل با دیگران، این است که هر مشارکت‌کننده در مخزن *خودش* کار می‌کند، نه یک شاخه‌ی مشترک روی مخزن اصلی؛ این باعث می‌شود این مدل برای تیم‌های بزرگ، حتی غیرقابل‌اعتماد یا ناشناس، هم امن و مقیاس‌پذیر باشد.

### جدول مقایسه‌ی نهایی

| مدل | پیچیدگی | بهترین کاربرد |
|---|---|---|
| GitHub Flow | کم | تیم‌های چابک با انتشار مداوم و مکرر |
| Git Flow | زیاد | پروژه‌های بزرگ با برنامه‌ی انتشار رسمی و نسخه‌بندی‌شده |
| Forking Workflow | متوسط (از نظر تنظیمات) | پروژه‌های متن‌باز و مشارکت‌کنندگان خارج از تیم اصلی |

### ۸.۵ چند قاعده‌ی عملی برای کار تیمی سالم

فارغ از این‌که کدام مدل را انتخاب می‌کنید، چند قاعده تقریباً در همه‌ی تیم‌های حرفه‌ای مشترک است:

- همیشه پیش از push، pull کنید تا از برخورد ناگهانی با یک تعارض بزرگ در لحظه‌ی آخر جلوگیری شود.
- شاخه‌های اصلی (مثل ‪main‬) را محافظت‌شده تنظیم کنید، به این معنا که push مستقیم به آن‌ها ممنوع باشد و همه‌چیز باید از طریق Pull Request و حداقل یک تأیید بررسی‌کننده عبور کند؛ این تنظیم از سمت خود سرویس (GitHub/GitLab)، نه Git خط‌فرمانی، اعمال می‌شود.
- مشخص کنید force-push (فرستادن اجباری تاریخچه‌ی بازنویسی‌شده) در چه شرایطی مجاز است؛ معمولاً فقط روی شاخه‌های شخصی خودتان، پس از یک rebase محلی، و هرگز روی شاخه‌های مشترک (دقیقاً همان قانون طلایی فصل ۴).
- پیام‌های کامیت را استاندارد کنید؛ بسیاری از تیم‌ها از قراردادی به نام Conventional Commits پیروی می‌کنند (مثل ‪feat: add login‬ یا ‪fix: correct off-by-one error‬) تا تاریخچه هم برای انسان و هم برای ابزارهای خودکار (مثل تولید خودکار changelog) خواناتر باشد.

### ۸.۶ حالا چه؟

در این فصل، از دنیای فردی به دنیای تیمی وارد شدیم: Fork کردن و تنظیم upstream، گردش‌کار کامل Pull Request از شاخه‌سازی تا ادغام، اصول بررسی کد، و مقایسه‌ی سه مدل رایج گردش‌کار، یعنی GitHub Flow، Git Flow، و Forking Workflow.

در فصل بعد، به سراغ ابزارهای پیشرفته‌تری می‌رویم که در پروژه‌های بزرگ‌تر و پیچیده‌تر کاربرد پیدا می‌کنند: مدیریت وابستگی‌های خارجی با زیرماژول‌ها، کار هم‌زمان روی چند شاخه با درخت‌های کاری چندگانه، خودکارسازی با قلاب‌ها، و تکنیک‌هایی برای کار با مخازن بسیار بزرگ.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| git remote add upstream URL | مخزن اصلی (پیش از فورک) را به‌عنوان یک ریموت دوم اضافه می‌کند. |
| git fetch upstream | آخرین تغییرات مخزن اصلی را دانلود می‌کند (بدون ادغام). |
| git merge upstream/main | آخرین تغییرات مخزن اصلی را در شاخه‌ی محلی ادغام می‌کند. |
| git checkout -b feature/NAME | یک شاخه‌ی ویژگی تازه برای کار روی یک تغییر مشخص می‌سازد. |
| git push origin feature/NAME | شاخه‌ی ویژگی را به فورک شخصی شما (نه مخزن اصلی) ارسال می‌کند. |
| (رابط وب) Compare & pull request | باز کردن یک Pull Request از شاخه‌ی شما به مخزن اصلی. |

</div>

<div dir="rtl" lang="fa" style="text-align: right;">

## فصل ۹

### <u>ابزارهای پیشرفته‌ی Git</u>

در فصل‌های قبل، تقریباً همه‌ی چیزهایی که یک توسعه‌دهنده در کار روزمره‌اش نیاز دارد را پوشش دادیم. در این فصل، به سراغ ابزارهایی می‌رویم که معمولاً در پروژه‌های بزرگ‌تر، پیچیده‌تر، یا با نیازهای خاص‌تر کاربرد پیدا می‌کنند: مدیریت وابستگی‌های خارجی با زیرماژول‌ها، کار هم‌زمان روی چند شاخه با درخت‌های کاری چندگانه، خودکارسازی با قلاب‌ها (hooks)، و بررسی جزئی مخازن بسیار بزرگ.

### ۹.۱ زیرماژول‌ها (Submodules): گنجاندن یک مخزن درون مخزن دیگر

فرض کنید پروژه‌ی شما به یک کتابخانه‌ی خارجی نیاز دارد که خودش هم یک مخزن Git مستقل با تاریخچه‌ی خودش است. زیرماژول به شما اجازه می‌دهد آن مخزن را، دقیقاً در یک کامیت مشخص، درون پروژه‌ی خودتان بگنجانید، بدون این‌که تاریخچه‌ی آن دو مخزن با هم قاطی شود.

برای افزودن یک زیرماژول:

</div>

<div style="text-align:left;">

```
$ git submodule add https://github.com/example/cool-library.git libs/cool-library
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، مخزن خارجی را در پوشه‌ی ‪libs/cool-library‬ کلون می‌کند، و یک فایل به نام ‪.gitmodules‬ در ریشه‌ی پروژه‌ی شما می‌سازد که نگاشت بین مسیر محلی و آدرس مخزن خارجی را ذخیره می‌کند. این فایل، خودش هم باید کامیت شود:

</div>

<div style="text-align:left;">

```
$ git add .gitmodules libs/cool-library
$ git commit -m "Add cool-library as a submodule"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نکته‌ی مفهومی مهم: مخزن اصلی شما، زیرماژول را با شناسه‌ی دقیق کامیتش (SHA) ردیابی می‌کند، نه محتوای واقعی فایل‌هایش؛ یعنی از دید مخزن اصلی، زیرماژول فقط یک اشاره‌گر به یک نقطه‌ی مشخص از تاریخچه‌ی یک مخزن دیگر است.

### کلون کردن پروژه‌ای که زیرماژول دارد

اگر کسی دیگر مخزن شما را کلون کند، به‌طور پیش‌فرض، پوشه‌ی زیرماژول *خالی* خواهد بود؛ باید صریحاً درخواست کند که Git محتوای زیرماژول‌ها را هم بیاورد:

</div>

<div style="text-align:left;">

```
$ git clone --recurse-submodules https://github.com/example/main-project.git
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر پروژه را بدون این فلگ کلون کرده باشید، می‌توانید بعداً هم زیرماژول‌ها را مقداردهی کنید:

</div>

<div style="text-align:left;">

```
$ git submodule update --init --recursive
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### به‌روزرسانی یک زیرماژول

برای به‌روزرسانی زیرماژول به آخرین کامیت شاخه‌ی مربوطه‌اش:

</div>

<div style="text-align:left;">

```
$ cd libs/cool-library
$ git pull origin main
$ cd ../..
$ git add libs/cool-library
$ git commit -m "Update cool-library to latest version"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

توجه کنید که کامیت آخر، در واقع فقط شناسه‌ی کامیت *جدید* زیرماژول را در مخزن اصلی ثبت می‌کند؛ محتوای واقعی زیرماژول همچنان در تاریخچه‌ی مستقل خودش نگه‌داری می‌شود.

### محدودیت‌های واقعی زیرماژول‌ها

باید صادقانه بگوییم: زیرماژول‌ها، با وجود کاربردشان، به دلیل تجربه‌ی کاربری نه‌چندان روان (فراموش کردن ‪--recurse-submodules‬، مشکلات دسترسی در محیط CI، و دشواری استفاده از ‪bisect‬ روی مخازنی که وضعیت زیرماژول‌شان مستقل از مخزن اصلی تغییر می‌کند) شهرت چندان خوبی در میان بسیاری از تیم‌های حرفه‌ای ندارند. جایگزین‌های رایج، بسته به نیاز واقعی پروژه، عبارت‌اند از: ادغام کامل کد در یک مخزن واحد (اگر وابستگی مشترک با پروژه‌ی دیگری نیست)، استفاده از پکیج‌منیجر زبان برنامه‌نویسی (npm، pip، Cargo، و مانند آن، که برای این هدف بسیار مناسب‌ترند)، یا در مقیاس‌های بزرگ‌تر، یک تک‌مخزن (monorepo) همراه با sparse-checkout که در بخش ۹.۴ همین فصل می‌بینیم.

### ۹.۲ کار هم‌زمان روی چند شاخه: ‪git worktree‬

تا این‌جا، همیشه فرض کردیم فقط یک نسخه از درخت کاری پروژه‌تان روی دیسک وجود دارد، و برای جابه‌جایی بین شاخه‌ها، از ‪checkout‬ یا ‪switch‬ استفاده می‌کنید. اما گاهی می‌خواهید *هم‌زمان* روی دو شاخه‌ی مختلف کار کنید، مثلاً وقتی وسط توسعه‌ی یک ویژگی هستید و یک باگ فوری روی ‪main‬ باید رفع شود، بدون این‌که مجبور باشید کار ناتمام فعلی‌تان را ‪stash‬ کنید.

‪git worktree‬ دقیقاً همین مشکل را حل می‌کند: به شما اجازه می‌دهد چند «درخت کاری» جداگانه روی دیسک داشته باشید که همه به همان یک مخزن ‪.git‬ متصل‌اند:

</div>

<div style="text-align:left;">

```
$ git worktree add ../hotfix-area hotfix-branch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، یک پوشه‌ی تازه به نام ‪../hotfix-area‬ می‌سازد که شاخه‌ی ‪hotfix-branch‬ در آن checkout شده است؛ در همان لحظه، درخت کاری اصلی شما دست‌نخورده باقی می‌ماند و روی همان شاخه‌ای که قبلاً بودید. حالا می‌توانید در یک پنجره‌ی ترمینال جداگانه، به آن پوشه بروید، رفع اشکال را انجام دهید، کامیت و push کنید، بدون این‌که کوچک‌ترین اثری روی کار ناتمام درخت کاری اصلی بگذارد.

برای دیدن فهرست همه‌ی درخت‌های کاری فعال:

</div>

<div style="text-align:left;">

```
$ git worktree list
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

وقتی کارتان با یک درخت کاری تمام شد، آن را حذف کنید:

</div>

<div style="text-align:left;">

```
$ git worktree remove ../hotfix-area
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۹.۳ خودکارسازی با قلاب‌ها (Hooks)

قلاب‌ها اسکریپت‌هایی هستند که Git، به‌طور خودکار، در نقاط مشخصی از چرخه‌ی کارش (مثل درست پیش از یک کامیت، یا درست بعد از یک merge) اجرا می‌کند. این قلاب‌ها در پوشه‌ی ‪.git/hooks‬ هر مخزن قرار دارند، و Git از قبل، برای هر نوع رویداد، یک فایل نمونه (با پسوند ‪.sample‬) در همان پوشه می‌گذارد که می‌توانید آن‌ها را فعال و سفارشی کنید.

### یک قلاب ساده‌ی pre-commit

فرض کنید می‌خواهید پیش از هر کامیت، مطمئن شوید هیچ کد نیمه‌کاره‌ای (مثل کامنت ‪TODO‬) وارد تاریخچه نمی‌شود. فایلی به نام ‪.git/hooks/pre-commit‬ بسازید (بدون پسوند):

</div>

<div style="text-align:left;">

```
#!/bin/bash
if git diff --cached | grep -q "TODO"; then
    echo "Commit blocked: found a TODO comment in staged changes."
    exit 1
fi
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

و آن را قابل‌اجرا کنید:

</div>

<div style="text-align:left;">

```
$ chmod +x .git/hooks/pre-commit
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

از این پس، هر بار که ‪git commit‬ می‌زنید، این اسکریپت به‌طور خودکار اجرا می‌شود. اگر با کد بازگشتی غیرصفر خارج شود (مثل مثال بالا)، خود کامیت هم لغو می‌شود.

### قلاب‌های رایج دیگر

- ‪pre-commit‬: پیش از ثبت هر کامیت؛ برای بررسی سبک کد، اجرای تست‌های سریع، یا جلوگیری از کامیت اطلاعات حساس.
- ‪commit-msg‬: برای بررسی یا اصلاح خودکار فرمت پیام کامیت (مثلاً اجبار به پیروی از Conventional Commits که در فصل ۸ دیدیم).
- ‪pre-push‬: پیش از ارسال تغییرات به یک ریموت؛ برای اجرای مجموعه تست‌های کامل‌تر پیش از این‌که کد به اشتراک گذاشته شود.
- ‪post-merge‬: بعد از هر ادغام موفق؛ مثلاً برای نصب خودکار وابستگی‌های تازه‌ای که ممکن است در کامیت‌های تازه اضافه شده باشند.

محدودیت مهم: قلاب‌ها فقط *محلی* هستند و هرگز با ‪git clone‬ برای دیگران کپی نمی‌شوند. اگر می‌خواهید همه‌ی اعضای تیم از قلاب‌های یکسانی استفاده کنند، باید از ابزارهای مکملی مثل Husky (برای پروژه‌های Node.js) یا اسکریپت‌های راه‌اندازی که این قلاب‌ها را در هر کلون تازه نصب می‌کنند، استفاده کنید.

### ۹.۴ بررسی جزئی یک مخزن بزرگ: ‪git sparse-checkout‬

اگر با یک مخزن بسیار بزرگ (مثل یک تک‌مخزن سازمانی با ده‌ها هزار فایل) کار می‌کنید، اما فقط به بخش کوچکی از آن نیاز دارید، دانلود و checkout کردن *همه‌چیز* اتلاف زمان و فضای دیسک است. ‪git sparse-checkout‬ به شما اجازه می‌دهد فقط زیرمجموعه‌ای از پوشه‌های مخزن را روی دیسک داشته باشید.

بهترین روش، ترکیب این ویژگی با کلون جزئی (partial clone) است تا حتی داده‌های شیء (blob) غیرضروری هم دانلود نشوند:

</div>

<div style="text-align:left;">

```
$ git clone --filter=blob:none --no-checkout https://github.com/example/large-monorepo.git
$ cd large-monorepo
$ git sparse-checkout set --cone services/payments/
$ git checkout main
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

فلگ ‪--no-checkout‬ در دستور clone ضروری است؛ بدون آن، Git تلاش می‌کند پیش از این‌که sparse-checkout فرصت محدود کردن دامنه را داشته باشد، کل درخت را روی دیسک بسازد. پس از این دستورها، فقط پوشه‌ی ‪services/payments/‬ روی دیسک شما ظاهر می‌شود؛ بقیه‌ی پوشه‌های مخزن، هرچند در تاریخچه‌ی Git وجود دارند، اصلاً روی دیسک نوشته نمی‌شوند.

نکته‌ی مفهومی مهم: sparse-checkout فقط روی *درخت کاری* اثر می‌گذارد، نه روی خود تاریخچه‌ی Git. یعنی همچنان تمام کامیت‌های تاریخچه، شامل فایل‌های خارج از دامنه‌ی sparse-checkout شما، در مخزن محلی‌تان وجود دارند؛ فقط روی دیسک، در پوشه‌ی درخت کاری، ظاهر نمی‌شوند.

برای افزودن پوشه‌ی دیگری به دامنه‌ی فعلی:

</div>

<div style="text-align:left;">

```
$ git sparse-checkout add services/notifications/
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

و برای بازگشت کامل به یک checkout معمولی (همه‌چیز روی دیسک):

</div>

<div style="text-align:left;">

```
$ git sparse-checkout disable
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۹.۵ حالا چه؟

در این فصل، با چهار ابزار پیشرفته آشنا شدید که هرکدام مسئله‌ی خاصی از پروژه‌های بزرگ و پیچیده را حل می‌کنند: زیرماژول‌ها برای گنجاندن مخازن خارجی (به‌همراه هشدارهایی درباره‌ی محدودیت‌های عملی‌شان)، درخت‌های کاری چندگانه برای کار هم‌زمان روی چند شاخه، قلاب‌ها برای خودکارسازی مراحل چرخه‌ی کاری، و sparse-checkout برای کار کارآمد با مخازن بسیار بزرگ.

در فصل پایانی، به سراغ مسائل نگهداری، بهینه‌سازی، و امنیت مخزن می‌رویم: چگونه سلامت مخزن خود را بررسی کنید، عملکرد آن را در طول زمان حفظ کنید، و کامیت‌های خود را با GPG امضا کنید تا اصالتشان قابل‌اثبات باشد.

### برای مرجع بعدی

| دستور | توضیح |
|---|---|
| git submodule add URL PATH | یک مخزن خارجی را به‌عنوان زیرماژول به مسیر مشخص اضافه می‌کند. |
| git clone --recurse-submodules URL | مخزن را همراه با محتوای کامل زیرماژول‌هایش کلون می‌کند. |
| git submodule update --init --recursive | زیرماژول‌های یک مخزن از‌قبل‌کلون‌شده را مقداردهی و به‌روز می‌کند. |
| git worktree add PATH BRANCH | یک درخت کاری تازه و جداگانه برای شاخه‌ی مشخص‌شده می‌سازد. |
| git worktree list | فهرست همه‌ی درخت‌های کاری متصل به مخزن فعلی را نمایش می‌دهد. |
| git worktree remove PATH | یک درخت کاری اضافی را حذف می‌کند. |
| .git/hooks/pre-commit (و مشابه) | اسکریپت‌های محلی که در نقاط مشخصی از چرخه‌ی Git خودکار اجرا می‌شوند. |
| git clone --filter=blob:none --no-checkout URL | مخزن را بدون دانلود کامل محتوا و بدون checkout اولیه کلون می‌کند. |
| git sparse-checkout set --cone PATH | فقط پوشه‌ی مشخص‌شده را در درخت کاری قرار می‌دهد. |
| git sparse-checkout add PATH | یک پوشه‌ی دیگر را به دامنه‌ی sparse-checkout فعلی اضافه می‌کند. |
| git sparse-checkout disable | به حالت عادی (همه‌ی فایل‌ها روی دیسک) بازمی‌گردد. |

</div>

<div dir="rtl" lang="fa" style="text-align: right;">

## فصل ۱۰

### <u>بهینه‌سازی، نگهداری و امنیت</u>

در فصل‌های قبل، همه‌ی مهارت‌های روزمره و پیشرفته‌ی کار با Git را پوشش دادیم. در این فصل پایانی، به دو موضوع تکمیلی می‌پردازیم که اغلب نادیده گرفته می‌شوند، اما برای مخازن بلندمدت و پروژه‌های حرفه‌ای اهمیت زیادی دارند: چگونه سلامت و عملکرد مخزن خود را در طول زمان حفظ کنید، و چگونه با امضای GPG، اصالت کامیت‌های خود را قابل‌اثبات کنید.

### ۱۰.۱ Git داده‌ها را چگونه ذخیره می‌کند: مفهوم شیء و پکیج

پیش از این‌که وارد دستورهای نگهداری شویم، باید یک مفهوم داخلی را بشناسیم. هر بار که کامیت می‌کنید، Git داده‌های تازه (فایل‌ها، درخت‌های پوشه، و خود کامیت) را به‌صورت اشیای مجزا، در پوشه‌ی ‪.git/objects‬، ذخیره می‌کند. این اشیای تازه، ابتدا به‌صورت «شیء آزاد» (loose object) روی دیسک نوشته می‌شوند؛ یعنی هرکدام یک فایل جداگانه‌اند. با گذشت زمان و تعداد کامیت‌های زیاد، این هزاران فایل کوچک، هم فضای دیسک را ناکارآمد اشغال می‌کنند و هم عملکرد Git را کند می‌کنند.

برای دیدن وضعیت فعلی این اشیا:

</div>

<div style="text-align:left;">

```
$ git count-objects -vH
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

خروجی چیزی شبیه به این خواهد بود:

</div>

<div style="text-align:left;">

```
count: 1247
size: 12.4 MiB
in-pack: 85634
packs: 2
size-pack: 340.2 MiB
prune-packable: 0
garbage: 0
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

‪count‬ تعداد اشیای آزادی است که هنوز فشرده و بسته‌بندی (pack) نشده‌اند، و ‪in-pack‬ تعداد اشیایی است که از قبل در فایل‌های فشرده‌ی «pack» جمع شده‌اند. هرچه ‪count‬ بزرگ‌تر باشد، زمان آن رسیده که نگهداری انجام دهید.

### ۱۰.۲ فشرده‌سازی و بسته‌بندی با ‪git gc‬

دستور ‪git gc‬ (مخفف garbage collection) مجموعه‌ای از وظایف نگهداری را در یک دستور واحد انجام می‌دهد: اشیای آزاد را در فایل‌های pack فشرده و بهینه می‌کند، فایل‌های pack موجود را در صورت لزوم ادغام می‌کند، اشیای غیرقابل‌دسترسی (که دیگر هیچ شاخه یا تگی به آن‌ها اشاره نمی‌کند و به‌اندازه‌ی کافی قدیمی شده‌اند) را حذف می‌کند، و ساختارهای کمکی مثل ‪commit-graph‬ را به‌روزرسانی می‌کند:

</div>

<div style="text-align:left;">

```
$ git gc
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

نکته‌ی خوب این است که Git، به‌طور خودکار، هنگام اجرای دستورهای معمولی، بررسی می‌کند آیا مخزن به‌اندازه‌ی کافی از آخرین نگهداری رشد کرده یا نه، و در صورت نیاز، خودش نسخه‌ی سبک‌تری از این عملیات (‪git gc --auto‬) را در پس‌زمینه اجرا می‌کند؛ یعنی برای اکثر کاربران، اجرای دستی ‪gc‬ چندان ضروری نیست.

با این حال، برای مخازن بسیار بزرگ یا پس از یک پاکسازی عمده (مثلاً حذف فایل‌های حجیم از تاریخچه)، اجرای دستی و حتی حالت تهاجمی‌تر آن می‌تواند مفید باشد:

</div>

<div style="text-align:left;">

```
$ git gc --aggressive
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

فلگ ‪--aggressive‬ زمان و توان پردازشی بیشتری صرف پیدا کردن بهترین روش فشرده‌سازی می‌کند. نکته‌ی مهم: این گزینه «دکمه‌ی جادویی سرعت» نیست؛ روی بسیاری از مخازن، بهبود آن نسبت به ‪gc‬ معمولی چندان محسوس نیست، و به همین دلیل توصیه می‌شود آن را فقط گاه‌به‌گاه (مثلاً ماهی یک‌بار روی مخازن بزرگ) اجرا کنید، نه به‌عنوان یک عادت روزمره.

### حذف فوری اشیای غیرقابل‌دسترسی

به‌طور پیش‌فرض، ‪gc‬ فقط اشیایی را حذف می‌کند که هم غیرقابل‌دسترسی باشند و هم به‌اندازه‌ی کافی قدیمی (پیش‌فرض حدود دو هفته)، تا reflog (که در فصل ۶ دیدیم) فرصت کافی برای بازیابی احتمالی آن‌ها داشته باشد. اگر مطمئن هستید به هیچ‌کدام از این اشیا نیازی ندارید و می‌خواهید بلافاصله فضای دیسک را آزاد کنید:

</div>

<div style="text-align:left;">

```
$ git gc --prune=now
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

هشدار: این گزینه باید با احتیاط استفاده شود، به‌خصوص درست پس از یک ‪rebase‬ پیچیده یا ‪reset --hard‬؛ اگر بعداً متوجه شوید به یکی از آن کامیت‌های «گم‌شده» نیاز دارید، ‪reflog‬ (شبکه‌ی ایمنی فصل ۶) دیگر نمی‌تواند کمکتان کند، چون خود اشیا هم پاک شده‌اند.

### ۱۰.۳ بررسی سلامت مخزن با ‪git fsck‬

اگر شک دارید مخزن شما دچار خرابی داده شده (مثلاً به‌خاطر یک خاموشی ناگهانی سیستم یا مشکل سخت‌افزاری دیسک)، ‪git fsck‬ (مخفف filesystem check) صحت داخلی همه‌ی اشیای مخزن را بررسی می‌کند:

</div>

<div style="text-align:left;">

```
$ git fsck --full
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

اگر بخواهید فهرست اشیای *غیرقابل‌دسترسی* (که هنوز حذف نشده‌اند، اما هیچ شاخه یا تگی هم به آن‌ها اشاره نمی‌کند) را ببینید:

</div>

<div style="text-align:left;">

```
$ git fsck --unreachable
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۱۰.۴ حذف دستی اشیای غیرقابل‌دسترسی با ‪git prune‬

‪git prune‬ یک دستور سطح‌پایین‌تر است که فقط یک کار مشخص انجام می‌دهد: حذف اشیای آزاد و غیرقابل‌دسترسی از دیسک. برخلاف ‪gc‬ که یک مجموعه‌ی کامل از وظایف نگهداری است، ‪prune‬ به‌تنهایی هیچ فشرده‌سازی یا بسته‌بندی‌ای انجام نمی‌دهد. به همین دلیل، در عمل، بیشتر پاکسازی واقعی از طریق ‪gc‬ یا از طریق ‪git fetch --prune‬ (که شاخه‌های ردیابی ریموتِ حذف‌شده را پاک می‌کند) انجام می‌شود، نه با فراخوانی مستقیم ‪prune‬.

اگر بخواهید پیش از حذف واقعی ببینید چه چیزی حذف خواهد شد:

</div>

<div style="text-align:left;">

```
$ git prune --dry-run
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۱۰.۵ خودکارسازی نگهداری با ‪git maintenance‬

نسخه‌های جدیدتر Git، یک راه بسیار ساده‌تر برای این‌که نگهداری به‌طور کامل خودکار و در پس‌زمینه انجام شود اضافه کرده‌اند:

</div>

<div style="text-align:left;">

```
$ git maintenance start
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، وظایف نگهداری دوره‌ای (مثل بسته‌بندی سبک هر ساعت و نگهداری کامل روزانه) را برای این مخزن ثبت می‌کند تا در پس‌زمینه، بدون نیاز به دخالت دستی شما، اجرا شوند؛ یک راه‌حل «تنظیم کن و فراموش کن» برای مخازنی که به‌طور مداوم فعال هستند.

### ۱۰.۶ چرا امضای کامیت اهمیت دارد

حالا به موضوع دوم و پایانی این کتاب می‌رسیم: امنیت. یکی از نکاتی که ممکن است تعجب‌آور باشد این است که فیلد «Author» یک کامیت Git، هیچ تأیید هویتی ندارد؛ هرکسی می‌تواند با تنظیم ‪git config user.name‬ و ‪user.email‬ به نام و ایمیل *هر شخص دیگری*، کامیتی بسازد که ظاهراً از طرف آن شخص است. برای پروژه‌های حساس یا زیرساخت‌های سازمانی، این یک نقطه‌ضعف واقعی است.

راه‌حل، امضای دیجیتال کامیت‌ها با GPG است؛ همان مفهومی که در کتاب اختصاصی GPG این مجموعه، با جزئیات کامل توضیح داده شده. در این‌جا، فقط به نحوه‌ی یکپارچه کردن آن با Git می‌پردازیم.

### پیش‌نیاز: داشتن یک کلید GPG

پیش از هر چیز، باید یک جفت‌کلید GPG داشته باشید. اگر ندارید:

</div>

<div style="text-align:left;">

```
$ gpg --list-secret-keys --keyid-format LONG
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

این دستور، شناسه‌ی کلیدهای موجود را نشان می‌دهد (چیزی شبیه به ‪3AR5C34371567CD2‬). اگر هیچ کلیدی ندارید، باید ابتدا یکی بسازید؛ نحوه‌ی کامل ساختن جفت‌کلید GPG، خارج از حوصله‌ی این کتاب است.

### معرفی کلید به Git

پس از داشتن شناسه‌ی کلید، آن را به Git معرفی می‌کنید:

</div>

<div style="text-align:left;">

```
$ git config --global user.signingkey 3AR5C34371567CD2
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### امضای یک کامیت واحد

برای امضای یک کامیت خاص، از فلگ ‪-S‬ استفاده کنید:

</div>

<div style="text-align:left;">

```
$ git commit -S -m "Add payment validation logic"
```

<div dir="rtl" lang="fa" style="text-align: right;">

### امضای خودکار همه‌ی کامیت‌ها

اگر می‌خواهید همه‌ی کامیت‌های آینده، به‌طور خودکار امضا شوند، بدون نیاز به تکرار ‪-S‬ در هر بار:

```
    Signed commit
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

برای بررسی برنامه‌ای (مثلاً در یک قلاب یا خط‌لوله‌ی CI) که یک کامیت مشخص معتبر است یا نه، از دستور اختصاصی زیر استفاده کنید که فقط همین یک کار را انجام می‌دهد:

</div>

<div style="text-align:left;">

```
$ git verify-commit HEAD
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### اجبار به پذیرش فقط کامیت‌های امضاشده هنگام merge

از Git نسخه‌ی ۱.۸.۳ به بعد، می‌توانید به Git بگویید هنگام ادغام یک شاخه، اگر کامیت‌های آن شاخه امضای معتبر نداشته باشند، عملیات را رد کند:

</div>

<div style="text-align:left;">

```
$ git merge --verify-signatures other-branch
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### نمایش وضعیت امضا در ‪log‬

می‌توانید فرمت خروجی ‪log‬ را طوری سفارشی کنید که وضعیت امضای هر کامیت را هم نشان دهد؛ نمادهای ‪%G?‬ در فرمت خروجی، وضعیت امضا (‪G‬ برای معتبر، ‪N‬ برای بدون امضا) را نشان می‌دهند:

</div>

<div style="text-align:left;">

```
$ git log --pretty="format:%h %G? %aN %s"
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### معرفی کلید عمومی به GitHub یا GitLab

برای این‌که سرویس‌هایی مثل GitHub، کامیت‌های امضاشده‌ی شما را با نشان «Verified» نمایش دهند (که در فصل ۸ هم به آن اشاره کردیم)، باید کلید *عمومی* خود را در تنظیمات حساب کاربری‌تان روی آن سرویس ثبت کنید. پس از این کار، هر کامیتی که با همان کلید خصوصی امضا کنید و push کنید، به‌طور خودکار با این نشان مشخص می‌شود؛ نشانی که به هرکس دیگری که به مخزن شما نگاه می‌کند، اطمینان می‌دهد آن کامیت واقعاً از طرف شما آمده.

### ۱۰.۷ یک اسکریپت نمونه‌ی نگهداری کامل

بیایید همه‌ی نکات این فصل را در یک اسکریپت نگهداری دوره‌ای ساده جمع‌بندی کنیم که می‌توان آن را، مثلاً هفتگی، روی مخازن مهم اجرا کرد:

</div>

<div style="text-align:left;">

```
#!/bin/bash
echo "Fetching and pruning stale remote-tracking branches..."
git fetch --all --prune

echo "Checking repository integrity..."
git fsck --full

echo "Running garbage collection..."
git gc

echo "Repository size after maintenance:"
du -sh .git
```
</div>
<div dir="rtl" lang="fa" style="text-align: right;">

### ۱۰.۸ جمع‌بندی کل کتاب

با پایان این فصل، سفر کاملی را طی کردیم: از پایه‌ای‌ترین مفاهیم Git (فصل ۱) و چرخه‌ی روزمره‌ی کار (فصل ۲)، تا شاخه‌بندی و ادغام (فصل ۳)، بازنویسی تاریخچه با rebase (فصل ۴)، همکاری از طریق مخازن ریموت (فصل ۵)، بازگرداندن اشتباهات (فصل ۶)، کاوش عمیق در تاریخچه (فصل ۷)، گردش‌کار تیمی حرفه‌ای (فصل ۸)، ابزارهای پیشرفته برای پروژه‌های بزرگ (فصل ۹)، و در نهایت، نگهداری و امنیت مخزن.

Git ابزاری است که، مثل بسیاری از ابزارهای قدرتمند دیگر، منحنی یادگیری‌اش در ابتدا کمی تند به نظر می‌رسد، اما هر مفهومی که یاد می‌گیرید، بلافاصله در عمل به کارتان می‌آید. اکنون شما نه‌فقط دستورهای Git، بلکه *مدل ذهنی* پشت آن‌ها را هم می‌شناسید؛ و همین درک عمیق است که به شما اجازه می‌دهد، حتی با موقعیت‌هایی که این کتاب مستقیماً به آن‌ها اشاره نکرده، با اطمینان روبه‌رو شوید.

### نگهداری و عملکرد

| دستور | توضیح |
|---|---|
| git count-objects -vH | تعداد و حجم اشیای آزاد و بسته‌بندی‌شده‌ی مخزن را نمایش می‌دهد. |
| git gc | مجموعه‌ای از وظایف نگهداری (فشرده‌سازی، حذف اشیای قدیمی، به‌روزرسانی ایندکس‌ها) را اجرا می‌کند. |
| git gc --aggressive | نگهداری کامل‌تر و کندتر؛ برای اجرای گاه‌به‌گاه روی مخازن بزرگ. |
| git gc --prune=now | اشیای غیرقابل‌دسترسی را بلافاصله حذف می‌کند (احتیاط: reflog دیگر کمکی نمی‌کند). |
| git fsck --full | صحت داخلی همه‌ی اشیای مخزن را بررسی می‌کند. |
| git fsck --unreachable | اشیای غیرقابل‌دسترسی‌ای که هنوز حذف نشده‌اند را فهرست می‌کند. |
| git prune --dry-run | نشان می‌دهد کدام اشیا حذف خواهند شد، بدون حذف واقعی. |
| git maintenance start | نگهداری دوره‌ای و خودکار در پس‌زمینه را برای این مخزن فعال می‌کند. |

### امضای GPG

| دستور | توضیح |
|---|---|
| git config --global user.signingkey KEY_ID | کلید GPG مورد استفاده برای امضای کامیت‌ها را تنظیم می‌کند. |
| git commit -S -m "MSG" | یک کامیت را با کلید GPG تنظیم‌شده امضا می‌کند. |
| git config --global commit.gpgsign true | همه‌ی کامیت‌های آینده را به‌طور خودکار امضا می‌کند. |
| git log --show-signature -1 | جزئیات کامل امضای آخرین کامیت را نمایش می‌دهد. |
| git verify-commit HEAD | اعتبار امضای یک کامیت مشخص را برنامه‌ای بررسی می‌کند. |
| git merge --verify-signatures BRANCH | فقط در صورت معتبر بودن امضای همه‌ی کامیت‌های شاخه، ادغام را انجام می‌دهد. |
| git log --pretty="format:%h %G? %aN %s" | وضعیت امضا (%G؟) را در کنار هر کامیت نمایش می‌دهد. |
